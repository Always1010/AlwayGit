# Validation and Local Updates

[简体中文](VALIDATION.md) | [Project home](../README.md)

This document maintains check entry points, acceptance scope, validation evidence, and local update procedures. Acceptance matrices describe the behavior that should be covered; recorded execution results apply only to the stated version and scope. `package.json` is the authority for the current source version.

<a id="check-selection"></a>

## Check Selection

Choose necessary checks for the change rather than running every command in sequence. Validate changes serving the same purpose together; after fixing a failure, rerun only affected checks. For documentation alone, check links, images, references to old filenames, and `git diff --check`, without rerunning functional tests. Host integration tests that open windows require the user's explicit consent under the [project rules (Chinese)](../AGENTS.md).

| Chinese/English resources and text calls | `npm run i18n:check` | Checks duplicate / unknown / unused keys, language and plural fallbacks, parameter consistency, review status, generated-file synchronization, UI presentation locations, and common hardcoded natural language; dynamic data and Demo examples are not treated as UI text |

### User Manual Screenshot Maintenance

First identify affected operation scenarios. Changes to surrounding toolbars, icons, or spacing usually require only updated entry text and a screenshot-difference note. When screenshots really need updating, run `npm run build` once, then `node scripts/capture-manual.mjs`. The script uses a headless browser and real workbench components from the current build. Isolated sample fixtures answer every RPC; no Git, Shell, native editor, window action, or remote connection occurs. It fixes the default theme (a white interface following a light host), language, font size, viewport, time zone, and sample time. Each scenario has an independent browser context. Dialogs are cropped to their bounds for readable text; narrow-sidebar pictures demonstrate component adaptation and do not constitute real VS Code container acceptance.

Previews go to ignored `artifacts/manual-capture/`. Use `--only=NN` to view one scenario or `--from=NN` to resume from a scenario; neither changes manual images. For a partial update, use `--only=NN`, inspect the result, and copy only the corresponding PNG to `docs/images/user-manual/`, retaining a clear operation region where possible. Do not copy everyday acceptance previews into the maintained directory. Only for an explicit user request or a dedicated manual redesign, use `node scripts/capture-manual.mjs --write` for full capture. Maintained images are replaced only after every scenario succeeds; partial capture cannot use `--write`. Scenario definitions live in this script; do not manually retain old image variants.

Both manuals share images, section anchors, and screenshot-source notes. New images must be referenced by both editions. When updating, check each affected image's actual entry point, object, count, direction, and accompanying text; delete invalid or unreferenced resources and retain real PNG encoding. Source notes record the actual capture date and source version. Partial replacements record new provenance by image number, retain the old source for other images, and note differences in surrounding UI. Demo feedback is not evidence of real Git or terminal execution. Native VS Code shell screenshots or host-behavior acceptance require separate visible-window permission under the project rules.

Afterward, check links and `git diff --check`, run `npx vitest run tests/help-content.test.ts`, build the final help resources, and run headless `node scripts/test-ui.mjs --help-only`. Also typecheck when help TypeScript changes. Screenshot changes do not justify the full functional suite. Record conclusions under “Validation Evidence and Coverage Boundaries” below.

## Packaging and Local Updates

```powershell
node scripts/package.mjs
```

Packaging detects the current platform, passes `--target` to VSCE, and builds through `vscode:prepublish`; no repeated build is needed immediately beforehand. It passes `--allow-star-activation` to explicitly accept the existing `*` startup activation and avoid recurring manual confirmation; this neither optimizes startup performance nor changes activation timing. You may specify `node scripts/package.mjs --target linux-arm64`, but the target must match the build machine; this does not cross-compile node-pty. Linux requires glibc plus Python, make, and a C++ compiler; source builds use Node.js 24.

The `.vscodeignore` release allowlist includes only the extension manifest/localization, README, icon, runtime programs, and Webview assets. Raw `docs/`, repository CI configuration, source maps, tests, and debug symbols are excluded. Complete bilingual offline manuals and all 40 screenshots remain in the Webview build, without a second copy of the original documentation images. Packaging generates a temporary README with relative documentation and language links rewritten to online GitHub `main` addresses. VSCE uses this copy while preserving the existing statistics SVG; the copy is deleted at completion. Repository READMEs retain relative links.

Builds clean old PTY directories and copy only node-pty runtime JS, licenses, and one complete native layout for the current target. A complete `build/Release` takes priority; otherwise target prebuilds are used, with either layout normalized to `prebuilds/<target>`. Windows retains ConPTY/WinPTY compatibility paths, helper processes, and Workers; Linux/macOS retain `pty.node` and `spawn-helper`. PDBs, other architectures, tests, type declarations, build scripts, and duplicate third-party binaries are excluded. After packaging, before replacing the fixed package, `verify-package.mjs` rejects unexpected files, duplicate entries, and missing required files, then extracts and checks extension identity, version, target platform, workspace host, and askpass execution permissions. It runs a real terminal lifecycle check in a temporary directory without relying on source node_modules. Only success replaces `artifacts/alwaygit.vsix`; the previous `artifacts/alwaygit-previous.vsix` and `artifacts/alwaygit-<版本>-<平台>.vsix` (version/platform placeholders) are retained. Failure preserves the original fixed package. Verification temporary directories are deleted at completion.

Check an existing package independently without rebuilding:

```bash
node scripts/verify-package.mjs artifacts/alwaygit.vsix
```

Run this check on the package's platform. `scripts/test-terminal-host.mjs` independently validates the current build's terminal helper, or accepts the path to an extracted `terminal-host.cjs`. Building/checking does not install or reload VS Code extensions.

The unified Windows/Linux installation entry is `scripts/install.mjs`. Existing Node.js is required. Source builds use Node.js 24 and require project dependencies installed with `npm ci` and native build tools on the target machine beforehand. The script does not install dependencies, Node.js, or toolchains. Installing an existing VSIX requires only Node.js and an available VS Code CLI, without project node_modules, Python, or a compiler.

Installation first calls the selected CLI's `--version` and checks compatibility with project `engines.vscode`. Incompatible/unreadable versions stop before building, replacing the fixed package, or installing. Installing an existing VSIX also checks the package's version requirements; packaging alone needs no VS Code. The current minimum is VS Code 1.106, required by the secondary-sidebar container contribution; lowering the manifest requirement alone cannot make 1.98 compatible. Updating a Desktop target below requirements requires updating the editor first; AlwayGit for Remote SSH should target Server. The script does not upgrade editors or switch installation locations automatically.

With no operation arguments in an interactive terminal, platform, operation, and location menus appear:

```bash
node scripts/install.mjs
# Linux convenience entry; same behavior:
bash scripts/install.sh
```

The platform menu recommends automatic detection and offers Windows x64/ARM64, Linux x64/ARM64, and macOS x64/ARM64; select the executing computer's OS/CPU. Explicitly choose build-and-install, install-existing-package, or package-only. Choose the location once: `desktop` (default) updates desktop VS Code on the executing machine; `server` updates its official VS Code Server. Paths/management entry points are located automatically, without another CLI/Server-version choice. Package-only does not ask for location. Noninteractive terminals require an operation argument. An explicit operation skips menus, defaults unspecified platform to detection, and defaults unspecified `--install-to` to Desktop. CI releases still cover Windows x64, Linux x64, and Linux ARM64.

On a remote Linux computer, choose an appropriate command in ordinary SSH or a VS Code terminal. These detect the platform by default; explicitly use `--target linux-x64` or `--target linux-arm64` if needed, matching the remote computer:

```bash
# Install the fixed package into the remote computer's desktop VS Code (default), without building:
bash scripts/install.sh --install-only
# Install the fixed package into the remote computer's VS Code Server for Remote SSH:
bash scripts/install.sh --install-only --install-to server
# Build, package, and install to Server; project dependencies and build tools must already be prepared:
bash scripts/install.sh --build-install --install-to server
# Install a package at a specified path; identity/version must match the current project:
bash scripts/install.sh --install-only --install-to server --vsix '/path/to/匹配当前平台的安装包.vsix'
# Package only, without calling VS Code:
bash scripts/install.sh --package-only
```

The Chinese filename placeholder above means “installation package matching the current platform.” Selecting a platform or Server neither connects to another machine nor cross-compiles: the target must match the executing machine. When a local computer connects to a remote computer, run the script remotely; Desktop then means the remote desktop edition and Server means the remote VS Code Server. In a local terminal, Desktop means the local desktop edition. Output includes package path, platform, location, actual CLI, version, and Profile; Server also shows the extension directory. Shell/PowerShell entries locate the unified script relative to themselves; relative `--vsix` paths resolve from the invocation directory.

Desktop detection skips Server/remote-cli entries in PATH/history and removes CLI remote-forwarding environment variables. Server prefers the instance for the current VS Code session; if unavailable/incompatible, it stops rather than hiding current-window limitations with another version. Ordinary SSH scans the current user's official installations, including `bin/<commit>` and `cli/servers/<实例>/server` (instance placeholder), and uses the newest available compatible management entry under that data root. Standard Stable storage takes precedence over Insiders; `VSCODE_AGENT_FOLDER` supports custom roots. Official `bin/code-server` manages extensions with the same explicit data/extension directories for installation and verification, without Remote CLI window IPC. Missing targets stop the operation; no Desktop/Server fallback or automatic Server preparation occurs.

After relevant checks pass, the original Windows entry remains available:

```powershell
scripts/update-local.ps1
# If the current version package was already generated successfully, skip another build:
scripts/update-local.ps1 -InstallOnly
# Specify target platform or package only:
scripts/update-local.ps1 -Target win32-x64 -PackageOnly
```

Without arguments, the PowerShell entry still builds and installs to Desktop. It supports existing `-CodePath`, `-Profile`, `-InstallOnly` plus `-Target`, `-Vsix`, `-PackageOnly`, and `-InstallTo desktop|server`; `-Vsix` requires `-InstallOnly`.

Installation record `artifacts/local-install.json` uses schema 3 and separates platform, host, Desktop/Server, and Server data roots. Selecting Server previously does not change the next Desktop default. Old `local` and schema-less Windows Desktop records migrate; old `remote` records are retained but not reused because their actual location is unknown. Desktop reuses a still-valid desktop CLI; Server redetects the current instance/latest available entry each time to accommodate updates. Override with `--code-path` / `--profile` or `ALWAYGIT_CODE_CLI` / `ALWAYGIT_VSCODE_PROFILE`; the CLI must belong to the selected location, and old environment variables cannot change Desktop/Server selection. Profile precedence is argument, environment, target's installation record, then default Profile. Specifying a nonempty Profile stops if the target CLI lacks `--profile`. Clear an old Profile with `--profile=` or PowerShell `-Profile ''`. Server management uses the default Profile and does not infer the Windows client's current Profile.

Before installation, built-in Node.js functionality reads package JSON/XML metadata and verifies extension identity, version, platform, and workspace host against the current project. Duplicate, damaged, oversized metadata and unsupported ZIP64/multivolume formats are rejected. This static check does not replace packaging's native terminal lifecycle validation. The script calls official CLI `--install-extension <VSIX> --force`, then verifies the installed `alwaygit-dev.alwaygit` version and package hash. Records are written only after installation and verification both succeed. Failure preserves the previous record, does not claim installation, and does not automatically uninstall or roll back. After success, reload the VS Code window when convenient; the script does not close/restart user windows. Replacing a VSIX alone does not establish an installed-extension update.

Focused unified-entry checks cover interactive choice, platform/package identity rejection, simulated CLI installation/version verification, record preservation on failure, Profile capability, target/record isolation, stopping on build failure, and Windows CMD quoting. Target-detection checks cover Remote CLI first in PATH, ordinary SSH, current session, multiple versions, old layouts, custom roots, symlinks, and missing selected targets; Linux entry syntax is checked. <a id="remote-tag-releases"></a>

## Remote Tag Releases

Pushing a stable `vMAJOR.MINOR.PATCH` Tag triggers `.github/workflows/release.yml` to validate/publish installable VSIX packages. Removing `v` must produce exactly the version in `package.json`, `package-lock.json`, and its root-package record. The Tag's Commit must already belong to remote `main`; any mismatch stops without creating a Release.

The workflow uses Node.js 24. Its shared validation job runs `npm ci`, type/i18n checks, one full Vitest run, and retains the existing statistics summary. After success, Windows x64, Ubuntu x64, and Ubuntu ARM64 jobs independently install native dependencies, build, package, and validate extracted terminals in parallel. Linux uses Ubuntu 22.04 / 22.04 ARM64 baselines rather than automatically advancing latest images.

Only after all three platforms succeed does a separate publish job use `contents: write` to create the same-name GitHub Release, uploading `alwaygit-<版本>-win32-x64.vsix`, `alwaygit-<版本>-linux-x64.vsix`, `alwaygit-<版本>-linux-arm64.vsix`, and corresponding `.sha256` files (version placeholders). It rechecks integrity/checksums for all six files before publishing and refuses to overwrite existing Releases. CI system Node.js validation does not substitute for VS Code Server's bundled Node.js or physical Linux ARM64 remote-device acceptance. Linux release packages support 64-bit glibc systems, Ubuntu 22.04+ / Debian 12+; older systems need environment-specific builds/checks.

Commit version files using Conventional Commits before creating an annotated Tag. Do not let `npm version` create a commit inconsistent with project rules. The following version is only an example; the Chinese commit subject is required by project convention:

```powershell
npm version 0.40.0 --no-git-tag-version
git add package.json package-lock.json
git commit -m "chore: 发布 0.40.0"
git tag -a v0.40.0 -m "AlwayGit 0.40.0"
git push origin main
git push origin v0.40.0
```

The Tag's Commit must include the release workflow before pushing the Tag. Historical Tags do not publish retroactively when a workflow is added later. Published Tags/Releases are never reused/overwritten; fix problems and increment the version. Downloadable GitHub Release VSIX packages are not Marketplace publication and do not cause automatic VS Code updates.

## Release Code Analysis

The README card and [full statistics page](https://always1010.github.io/AlwayGit/index.en.html) show the latest successfully released stable version, taking version/Commit directly from its Tag. Ordinary branch pushes, PRs, and local edits do not update the card. Only after a `vMAJOR.MINOR.PATCH` push and successful Release validation/publication does `.github/workflows/repository-stats.yml` analyze that Tag and deploy GitHub Pages. The README image is unavailable before the first deployment.

Counting rules:

- File totals/types come from the Tag snapshot via `git ls-tree`, including source, tests, scripts, configuration, locks, documentation, images, and generated code. Runner dependencies, build output, and untracked files are not scanned. Extensions are lowercase; extensionless files have a separate category, and dotfiles such as `.gitignore` use their names. Submodule statistics are unsupported; encountering one stops and requires a counting policy.
- Language shares use bytes of owned source, including source, tests, and maintenance scripts. `.ts/.tsx` combine as TypeScript; `.js/.jsx/.mjs/.cjs` as JavaScript; CSS, HTML, PowerShell, and Shell are also recognized. JSON/Markdown/SVG count only in file analysis. Declarations, `src/i18n/generated.ts`, `generated/`, `.generated.*`, minified code, and recognized dependency/third-party/build directories are excluded from language shares; symlinks are not source. This need not match GitHub Linguist exactly.
- Test counts reuse the same Release `npm test` Vitest JSON report. Individual cases count, parameterized cases count expanded results, and `describe` groups do not count. The card shows total, passed, skipped, and todo counts; it is not coverage and excludes desktop/UI tests not run in Release. Raw reports/internal paths are not published to Pages.

Repository administrators must configure GitHub for initial enablement:

1. Free accounts need a public repository. Under **Settings → Pages → Build and deployment → Source**, select **GitHub Actions**. No custom domain, server, or generated-file branch is required.
2. Check deployment rules at **Settings → Environments → github-pages**. With **Selected branches and tags**, allow both `v*` release Tags and default branch `main`; the latter supports manual recovery from the default branch. Check that official Actions used by workflows are permitted.
3. Merge this feature into main before pushing a new release Tag. Consolidate deployment content for existing Pages sites first: this workflow uploads the complete statistics site, and separate workflows must not overwrite the same site independently.

`scripts/repository-stats.mjs` generates Chinese `repository-stats.svg` / `index.html` and English `repository-stats.en.svg` / `index.en.html` from the same Tag snapshot and original test summary. Both pages list every file type and offer language switching; they share `repository-stats.json`, with identical data and counting rules. The Chinese README links to the Chinese card and page, while the English README links to their English counterparts. Both are deployed as of `v1.5.3`. The card shows the top eight types and aggregates the rest. Generated files live in ignored `artifacts/` and deploy via `upload-pages-artifact` / `deploy-pages`, without Git commit/push or a `gh-pages` branch. Initial scripts, workflows, and README references are ordinary project commits; later generated output does not enter Git.

Deployment uses read-only repository/Actions and Pages/OIDC publishing permissions, without code-writing permission. Deployments serialize, verify the original Release run's workflow/Commit/report identity, then inspect published stable versions and the current Pages version; older versions cannot overwrite newer ones. Statistics/Pages failures do not retract an existing Release; the previous deployed card remains available, with failure details in Actions. Pages publication/GitHub image caching can delay display; the card version identifies the statistics target.

Release saves successful test counts, Tag, Commit, repository, and run ID in `release-test-summary-<Tag>`, requesting 90-day retention (subject to repository limits). Recovery does not rerun tests/package: in **Actions → Release repository statistics → Run workflow**, select the default branch and enter `tag` and original **Release VSIX** `release_run_id` (the number in `/actions/runs/<ID>`). Recovery only supports successfully published stable Tags containing this feature. Original statistics Artifacts must remain downloadable; expiry/deletion explicitly fails rather than presenting rerun results as original Release tests. Failed statistics jobs may also be rerun directly; do not rerun the entire Release-creation process for card failures.

Focused check: `npx vitest run tests/repository-stats.test.ts`. It covers Tag snapshot isolation, language/type rules, executed-case counts, report/version identity, consistent bilingual pages/cards and complete deployment assets, output escaping, original release verification, and prevention of older-version overwrites. Do not commit generated data/reports.
