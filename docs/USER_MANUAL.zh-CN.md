## 快速开始：完成第一次提交

准备一个已有 Git 历史的练习仓库，确认当前分支正确且没有进行中的 Git 操作。首次安装见 [安装与启动](#section-01-02)。

1. 打开 AlwayGit 启动侧栏，点击 **Show Git Workbench**。在 Repositories 的 **Add…** 中添加仓库，然后双击仓库或按 Enter 进入。
2. 在 VS Code 中编辑并保存文件。回到工作台，单击中间的 **Working Tree**，在 Unstaged 中单击文件检查底部 Diff。
3. 右键准备提交的文件并执行 **Stage**。在 Staged 中再次检查将提交的实际内容。
4. 点击 Staged 标题中 Unstage 右侧的 **Commit…**（也可点击顶部 Commit），在浮窗填写 Commit Message，再点击 **Commit**。Commit 只保存 Staged 内容，其他未暂存修改会留在工作区。
5. 在结果栏点击 **View Commit**，或从 History 打开新提交，核对提交说明、文件清单与剩余修改。

**结果：** 新提交出现在历史中，内容与检查过的 Staged 一致。本地 Commit 后，可按 [远程协作](#chapter-08) 将提交 Push 到远端。

Commit 失败时保留草稿，展开错误详情，处理 Git 身份、钩子或提示的其他原因后重试。

## 安装与认识工作台

AlwayGit 把 Git 的仓库导航、提交历史、文件状态与只读差异放在 VS Code 编辑器区域。第一次使用时，先在练习仓库完成“编辑 → Stage → 检查 Staged → Commit”的闭环，再进行远程同步或历史改写。

截图主要采用英文界面；正文在说明截图时保留必要的英文按钮名称，便于定位操作。简体中文界面会翻译提交、获取、推送、合并、暂存、标签和工作树等普通动作与对象，并保留 Rebase、Cherry-pick、Graph、Stash、HEAD、Index 和 Diff 等核心 Git 术语。

<a id="section-01-01"></a>

### 安装前准备

准备 VS Code 1.95 或更新版本。基础功能要求 Git 2.40 或更新版本；所选文件 Stash 保存和 Apply / Pop 隔离恢复要求 Git 2.43 或更新版本。使用可信来源提供的 AlwayGit VSIX 安装包；已有项目应先是有效 Git 仓库。

<a id="section-01-02"></a>

### 安装 VSIX 并启动

**前提：** 已取得安装包，VS Code 能使用 Git；项目工作区已经由你确认可信。

1. 打开 VS Code 的扩展视图，在视图菜单中选择 Install from VSIX…，选择 AlwayGit 的 VSIX 文件。
2. 安装后，在扩展详情中核对 AlwayGit 的已安装版本与安装包对应；若 VS Code 提示重新加载，完成重新加载。
3. 点击活动栏中的 AlwayGit 图标，再点击 Show Git Workbench。也可从命令面板执行 AlwayGit: Show Workbench。
4. 首次进入后，通过 Repositories 的 Add… 添加仓库，然后双击目标仓库进入。

**结果：** 编辑器区域出现 AlwayGit 工作台；仓库加载后，能看到对应分支和历史。

**注意：** 打开启动侧栏本身不会自动新建工作台。Show 会优先回到当前窗口已有的工作台。

**排错：** 若 Git 不可用，检查安装和 VS Code 的 Git 路径；若工作区处于受限模式，仅在确认项目可信后再更改信任设置。

### 选择界面语言

1. 点击右上角齿轮打开 Settings，进入 General → Language（常规 → 语言）。
2. 在显示语言列表中选择 English 或简体中文，界面会立即预览所选语言。

**结果：** 工作台使用所选语言，重新打开设置后仍保留已应用的选择。

### 认识四个区域

![图 03  左侧仓库与引用 中间历史 右侧详情 底部只读 Diff](images/user-manual/figure-03.png)

| 区域 | 用途 | 先看什么 |
| --- | --- | --- |
| 左侧导航 | 仓库、项目分组、分支、远端、Tag、Stash、工作树 | 当前仓库和当前分支 |
| 中间 History | 提交图、搜索、引用范围、Working Tree | 你要查看的提交或未提交修改 |
| 右侧详情 | 提交文件列表或 Working Tree 文件列表 | 变更文件与 Staged 范围 |
| 底部标签面板 | 固定 Diff 预览与多个内嵌终端 | 当前文件差异或终端工作目录 |

底部加号创建一个终端标签，以当前仓库根目录启动；旁边下拉可选择默认 Shell、PowerShell、cmd 或 Bash（需在宿主安装）。终端标签与 Diff 共用高度；切换仓库不会改变已有终端目录。单击文件切回 Diff，后台刷新不切换标签。

终端可双击标签重命名，或使用工具栏清空显示；Shell 退出后保留输出和退出码，并显示重新启动按钮。关闭标签结束 Shell，收起面板或隐藏工作台继续运行。“全部标签”列表方便切换较多标签，最大化按钮临时扩展面板。选中文本后 Ctrl+C / Ctrl+Shift+C 复制，Ctrl+Shift+V 粘贴；没有选择时 Ctrl+C 中断 Shell 命令。关闭工作台或重载 VS Code 后终端不恢复，命令和输出不保存。也可以从命令面板执行“AlwayGit：新建内嵌终端”，默认快捷键为 Ctrl+Alt+Shift+T（macOS 为 Cmd+Alt+Shift+T）。

<a id="section-01-05"></a>

### 修改如何进入一次提交

Working Tree 是磁盘上的工作文件；Index 是下一次提交的准备区；Commit 是已经保存到 Git 历史的版本。Stage 把所选文件当前的修改放进 Index。普通 Commit 默认提交 Index 内容；统一列表中的“提交所选文件”也支持自动暂存所选未暂存文件后提交。

<a id="chapter-03"></a>

## 工作区和提交

提交前最重要的检查点是 Staged。同一文件同时出现未暂存和已暂存条目并不矛盾：Index 已保存一个版本，而磁盘文件在暂存后又发生了修改。

设置 → 界面 → 文件列表可选择默认的分组列表或统一变更列表。统一列表先显示未暂存，再显示已暂存，每类按文件名排序；有冲突时置于最前。同路径的两种版本各占一行，点击查看对应差异。统一模式顶部 Stage All、Unstage All、Discard All 带图标和文字，固定处理完整仓库，筛选及选择不改变范围；Discard All 仅丢弃未暂存更改，保留已暂存内容。

| 状态或分组 | 含义 | 推荐动作 |
| --- | --- | --- |
| Conflicts | Git 尚有未解决的冲突条目 | 先阅读“合并与冲突处理” |
| Unstaged | 磁盘内容尚未放入下一次提交的准备区 | 查看 Diff，选择要暂存的文件 |
| Staged | Index 中准备提交的变更 | 检查这一区域的 Diff 后再 Commit |
| M / A / D / R | 修改 / 新增 / 删除 / 重命名 | 同时核对文件名与完整父目录 |
| ? / ! | 未跟踪 / 冲突 | 确认是否应纳入版本或先解决冲突 |

<a id="section-03-01"></a>

### 检查一个文件的实际差异

**前提：** 已保存编辑器中的修改。

1. 单击 Working Tree，然后单击对应分组中的文件。
2. 检查底部 Diff 标题中的文件和比较对象；尤其确认当前看的是 Staged 还是 Unstaged。
3. 用上一处、下一处箭头浏览每个修改块，留意新增、修改、删除统计。
4. 文本文件需要编辑完整内容时，使用 Edit in VS Code；保存后返回工作台重新检查。图片和其他二进制文件只能在 AlwayGit 预览中查看。

**结果：** 你能解释准备保留的每块改动，并确认比较来源正确。

**注意：** 底部 Diff 只读，不能在其中直接改文件。PNG、JPEG 和 WebP 会左右并排显示并支持缩放、同步滚动、适应面板、100% 和最大化；其他二进制、超限图片或非法编码内容显示说明。图片和其他二进制禁用 VS Code 编辑与原生 Diff。

**排错：** 内容未更新时先确认编辑器已保存，再 Refresh；仍异常则查看输出与错误详情。

### 暂存或取消暂存指定文件

**前提：** 没有未处理冲突；清楚下一次提交的文件范围。

1. 在 Unstaged 中单击目标文件。多选时使用 Ctrl/Cmd 或 Shift。
2. 右键已经选中的文件，选择 Stage。右键未选文件会先把范围变为该单个文件。
3. 到 Staged 中检查结果。若选错，在 Staged 中右键对应文件并执行 Unstage。
4. 若确实要处理整个分组，使用分组标题的 Stage All 或 Unstage All，并核对确认数量。

**结果：** Staged 只包含这次提交需要的变更；Unstage 后修改仍保留在工作区。

**注意：** 本版本按整个文件操作。可在工作区摘要下面搜索文件名或相对路径，忽略大小写；点击清除图标恢复全部文件。分组模式标题按钮无筛选时处理全部对应分组，有筛选时只处理匹配文件，并在悬浮提示和确认中显示范围，不代表当前选中的几项；局部选择使用文件右键菜单。Ctrl/Cmd+A 只全选可见文件。搜索不改变实际 Staged 范围；普通 Commit 默认勾选全部已暂存文件，可以在提交清单中取消部分文件。

<a id="section-03-03"></a>

### 提交新增 删除和重命名

**前提：** 在 VS Code 资源管理器中进行文件整理，重要内容已有备份。

1. 新增文件后保存；删除文件前确认不再需要。重命名时选中文件并按 F2，输入新名称。
2. 回到 Working Tree，检查新增问号、删除 D 或重命名状态。重命名暂时显示为旧路径 D 与新路径问号时，先核对二者内容。
3. 明确选中相关路径并 Stage，再到 Staged 检查。Git 可能将成对的删除与新增识别为 R。
4. 提交后直接打开 History 中的新提交，确认最终的路径与内容。

**结果：** 新增、删除或重命名进入同一次预期提交；原有内容关系经过检查。

**注意：** 重命名识别取决于内容相似性。不要只根据提交前的 D 和问号就误判文件丢失。

<a id="section-03-04"></a>

### 提交并保留未完成修改

**前提：** 至少有一个 Staged 文件，提交说明已准备好。

1. 逐个检查 Staged 文件，包括删除和重命名。
2. 点击 Staged 标题中 Unstage 右侧的 Commit…，在浮窗填写 Commit Message。确认当前仓库、分支和文件清单（默认勾选全部 Staged，可取消部分文件），点击 Commit 或按 Ctrl/Cmd+Enter；Enter 用于换行。
3. 在 History 中单击新提交，核对实际文件列表；再回到 Working Tree 检查剩余未提交变更。
4. 若还存在 Unstaged 修改，可继续编辑或暂存，另作一次提交。

**结果：** 历史新增一条提交；仅 Index 中的内容进入该提交。

**注意：** Commit 草稿按仓库自动保存，Cancel、关闭、Esc 或点击遮罩均保留完整 Message，下次打开或重开工作台时恢复；提交失败也保留。提交成功后清空本次使用的草稿。尚未 Stage 也可打开浮窗写草稿，实际提交按钮会提示前置条件。成功结果中的 View Commit 打开本次操作返回的新提交；仍应检查实际文件内容。

**排错：** 失败时展开 Git 错误；保留草稿，先处理原因，再重新核对 Staged 范围。

统一列表中右键选择“提交所选文件…”时，浮窗只列出当次选中的文件，每个路径一行，可取消勾选。已暂存条目提交 Index 版本；未暂存条目提交最新已保存的磁盘版本，并在执行时自动暂存。同路径两种条目都选中时按未暂存版本提交一次。未暂存条目同时有已暂存更改时显示“合并提交”，上方提示两部分一并提交。未选文件的暂存内容保留，取消浮窗不改变 Index。Git Hook 和签名正常执行；Hook 可格式化所选文件，但若最终提交包含范围外更改，会在更新 HEAD 前拒绝提交并保留原有暂存内容。Hook 对磁盘文件的修改可能仍保留，须检查后再提交。活动 Git 操作中应检查并提交完整暂存结果。

![图 08 所选文件提交清单，可取消勾选，合并提交用一条提示说明两部分一并提交](images/user-manual/figure-08.png)

### 修改上一次提交

**注意：** Amend 会改变提交 ID。若原提交已被推送或被别人使用，先与协作者协调。完成后可通过结果栏的 View Commit 或 History 核对新记录。活动 Git 操作期间不能 Amend。

**前提：** 已确定当前 HEAD 就是要替换的提交；最好尚未分享给其他人。

1. 仅修改提交说明时可保持 Staged 为 0；需要补充文件内容时，先编辑、保存并 Stage 对应文件。
2. 打开 Commit 浮窗并勾选 Amend；草稿为空时载入当前提交说明，已有草稿不会被覆盖。核对将替换的 HEAD，修改提交说明。每次重新打开浮窗时 Amend 默认关闭。
3. 检查暂存内容与说明，确认后点击 Amend Commit；本地操作可以直接执行，点击前就要核对完整。
4. 到历史中确认替换结果与新的提交 ID。

**结果：** 当前提交被新提交替换，而不是在其后简单增加一条。

**排错：** 想撤销已分享提交的影响时，通常优先使用 Revert；不确定时先创建备份分支。

![图 11  Amend 后从 History 核对新说明与新提交 ID 不依赖完成横幅](images/user-manual/figure-11.png)

### 丢弃不需要的未暂存修改

**注意：** Discard 会丢弃所选未暂存内容；所选未跟踪文件会从磁盘删除。未提交内容可能没有可恢复的 Git 历史，不能承诺一定能找回。

**前提：** 已确认所选修改不需要保留；必要内容已提交、Stash 或另行备份。

1. 在 Unstaged 中选择目标文件，右键选择 Discard…。
2. 阅读确认浮窗中的路径清单与丢弃说明，逐项确认；若接着出现 VS Code 原生 Proceed 确认，再核对一次后继续。
3. 只有想丢弃全部 Unstaged 时才使用标题的 Discard All…。也可以直接右键图表 Working Tree 节点，选择“丢弃全部未暂存更改…”；节点菜单不受右侧筛选和选择影响，不必先打开文件列表。
4. 执行后查看剩余 Unstaged 和 Staged，确认作用范围。

**结果：** 被确认的未暂存修改被丢弃；同一文件已经在 Index 中的内容仍应保留。

需要同时丢弃暂存和未暂存内容时，右键 Working Tree 节点选择“丢弃全部更改…”。确认框会明确说明暂存区也将清除，已跟踪内容恢复至当前提交，新增及未跟踪文件删除，分支和已提交历史不变；尚无提交时清空暂存区并删除其中的新增文件。其余忽略文件保留。有冲突或正在进行的 Git 操作时，先完成或中止操作。菜单另提供全部暂存、全部取消暂存和 Stash 所有更改。

大文件列表按视口显示，筛选和全选仍覆盖完整匹配范围；Discard 没有 10,000 文件的数量上限，内部自动分批并显示进度。确认范围变化或操作部分失败后，点击“重新检查剩余更改”，核对新清单再确认。

**排错：** 若误操作，立即停止进一步写入，检查编辑器本地历史、备份或已有 Stash；不要继续做 Reset 或清理。

<a id="chapter-04"></a>

## 历史和差异比较

引用复选框控制“看哪些历史”，分支名称和行选择控制“操作谁”。勾选一个分支不会切换到该分支。

<a id="section-04-01"></a>

### 筛选历史并定位当前版本

**前提：** 仓库已有提交。

1. 在左侧勾选本地或远端分支；多个分支显示它们可达提交的并集。需要单独查看 Tag 历史时，从 Tag 右键菜单选择 Show Only This Tag History。
2. 用 Show Only This Branch History 或 Show Only This Tag History 只看目标历史；用 Locate Tag Commit in Graph 定位 Tag 指向的提交。
3. 使用 Local Branches 下方预设快速显示全部本地分支或仅当前分支。
4. 切换范围时，History 的原有摘要行临时显示正在加载的范围；失败会保留原图，并在同一行提供重试入口。
5. 用图表标题栏、搜索框前的返回图标恢复上一历史视图。存在搜索条件或图表范围不是当前分支时，旁边会出现 target 图标；用它清除搜索和标签范围，并定位 HEAD。Locate HEAD 保留已有范围，适合只找当前版本。浏览记录只在当前工作台会话中保留；很深或已过期的历史会重新读取并回到首屏。

**结果：** History 显示与你选定引用范围一致的提交图。

**注意：** Working Tree 是虚拟节点，不是历史 Commit。过滤掉 HEAD 后，它仍可能独立显示，且不会算入真实历史数量。

<a id="section-04-02"></a>

### 搜索提交信息并回到完整历史

**前提：** 知道提交说明中的关键词。

1. 在 History 的提交搜索框输入关键词。
2. 查看“提交搜索结果”和匹配数量；数量带加号时还存在未加载的匹配项。
3. 单击一个匹配提交，检查右侧详情。
4. 使用“在完整历史中定位”图标，清空搜索并在当前引用范围中定位该提交；也可手动清空搜索。

**结果：** 搜索时按消息筛选；回到完整历史后恢复 Graph 与列宽。

**注意：** 搜索结果隐藏 Graph，因为中间不匹配的提交可能缺失；不要把“没有连线”理解为历史损坏。

**排错：** 找不到目标时，检查关键词和引用筛选范围；不要假定搜索覆盖未选择的所有分支。

![图 13  搜索 guide 时隐藏 Graph 保留消息与提交详情](images/user-manual/figure-13.png)

<a id="section-04-03"></a>

### 查看提交内容与合并父提交

**前提：** 目标提交位于已加载历史中。

1. 单击 Commit 行，阅读提交说明、作者、时间及变更文件。
2. 用文件路径筛选框缩小 Changed Files；匹配完整仓库相对路径，不区分大小写。
3. 单击文件查看 Diff。若是 Merge Commit，在 Parent 选择器中选择要比较的父提交。
4. 文本文件需要完整内容时，使用原生 Open Diff；需要改当前工作区文本文件时，使用 Edit in VS Code。图片和其他二进制只使用底部预览。

**结果：** Diff 对应当前所选 Commit、Parent 和文件。

**注意：** 不同 Parent 会得到不同差异。历史详情中的编辑入口操作当前工作区文件，不会直接修改旧提交。

<a id="section-04-04"></a>

### 比较两个提交

**前提：** 知道比较的两个版本；二者已加载。

1. 单击第一个 Commit，再按 Ctrl/Cmd 单击第二个，使选择总数恰好为两个。
2. 右侧自动进入 Compare Commits。核对左右两端提交；有祖先关系时祖先放在左侧，否则遵循选择顺序。
3. 单击差异文件查看 Diff；需要反向理解新增和删除时点击交换按钮。
4. 取消选择到只剩一个 Commit，回到单提交详情。

**结果：** 差异列表和底部 Diff 展示两端版本之间的变化。

**注意：** 选择三个或更多提交会转回最后操作的提交详情，并保留多选供批量操作；不是多版本同时比较。

![图 14  恰好选择两个 Commit 后自动比较 右侧显示两端版本和文件](images/user-manual/figure-14.png)

<a id="section-04-05"></a>

### 阅读和导航差异

**前提：** 底部 Diff 已打开目标文件。

1. 观察当前文件的新增、修改、删除块数量。历史 Commit 默认显示“文件 2/5 · 修改 1/3”，分别表示文件位置和该文件内的修改块位置。
2. 点击上一处或下一处，默认按当前 Commit 的变更文件顺序循环。向下跨文件定位下一文件首处，向上跨文件定位上一文件末处，整个 Commit 首尾循环；Merge Commit 沿用当前 Parent，不切换 Commit。
3. 想只浏览一个文件时，在设置 → 界面 → Diff 中把“Diff 导航范围”改成“当前文件”并应用。此模式显示“当前 / 总修改块”，只有一块时，两枚按钮都可重新定位该块。此阅读偏好保存在用户设置，并跨窗口共享。
4. 长行使用横向滚动；需要更大阅读区时拖动分隔线。收起 Diff 再展开可继续阅读，换文件后重新核对比较标题。

**结果：** 可选择逐块检查整个 Commit 或当前文件；相邻变更行计为一个连续修改块。

**注意：** 整个 Commit 模式包含路径筛选隐藏的文件，标题显示实际文件路径，文件列表会提示当前文件被隐藏。二进制及没有文本修改块的文件自动跳过，仍可手动查看；读取失败时停止并显示错误。若提示预览截断，统计和导航仅覆盖已预览内容；到原生 Diff 或编辑器查看完整内容。Working Tree、Stash 和 Commit 比较仍在当前文件内循环。

<a id="chapter-05"></a>

## 分支与历史版本

分支是一个可移动的版本引用。创建分支、切换分支和筛选分支历史是三个独立动作；执行前先读按钮名称与完成反馈。

<a id="section-05-01"></a>

### 创建分支或创建后立即切换

**前提：** 起点已确认；工作区修改已妥善保存。

1. 在 Local Branches 标题点击 Create Branch…；也可右键指定分支或 Commit，从固定起点创建。
2. 核对对话框显示的起点，输入新分支名，例如 feature/readme。
3. 处理名称提示。同名、非法名称和父子路径冲突必须先改名。
4. 只想建立引用时选择 Create Only（仅创建）；要开始在新分支工作时选择 Create and Checkout（创建并切换）。
5. 读取完成反馈，并用当前分支标记确认是否真正切换。

**结果：** 新分支创建成功；是否切换与所选动作一致。

**注意：** 例如已有 feature/readme 时，不能再创建 feature；已有 feature 时，也不能创建 feature/readme。

**排错：** 若创建成功但 Checkout 被修改阻挡，新分支可能已经保留。先检查反馈，不要盲目再次创建同名分支。

![图 15  创建分支时明确起点 并区分 Create Only 与 Create and Checkout](images/user-manual/figure-15.png)

<a id="section-05-02"></a>

### 切换本地分支并处理受阻

**前提：** 目标不是当前分支，也没有被另一个 工作树 占用。

1. 双击目标本地分支，或右键选择 Checkout…。
   执行时会显示工作台自己的居中进度弹窗；完成并更新界面前，背景操作与快捷键暂时锁定。
2. 若提示可能覆盖修改，阅读受影响文件，不要直接丢弃。
3. 按目的选择先 Commit、先 Stash，或使用明确提供的 Stash Changes & Checkout。
4. 切换后确认当前分支三角形与 Working Tree 文件状态。

**结果：** 当前分支改变，工作目录与目标版本匹配，需保留的修改仍有可靠去处。

**注意：** 被其他 工作树 使用的分支不能直接在当前目录检出；可打开提示中的那个 工作树。

**排错：** 有冲突或正在进行的操作时，先完成或 Abort。单击分支名称只定位，不代表 Checkout 已执行。

![图 16  Checkout 对话框明确目标分支 main 并提示覆盖保护](images/user-manual/figure-16.png)

<a id="section-05-03"></a>

### 把远程分支转为本地跟踪分支

**前提：** 已经 Fetch，远端引用是你希望使用的最新状态。

1. 双击远程分支，或右键选择 Checkout as Local Branch…。
2. 核对远程来源和本地分支名；默认去掉远端前缀并保留目录结构。
3. 已有正确跟踪分支时选择复用；出现同名 upstream 冲突或路径冲突时，先修改名称。
4. 按需要保留或取消 Checkout 选项，确认创建或复用。
5. 要批量准备多个跟踪分支时，在同一 Remote 或目录上使用 Create Local Tracking Branches…，核对逐项结果。

**结果：** 本地分支跟踪正确的远程来源；批量创建流程保持当前分支。

**注意：** 这个动作不会自动 Fetch 或 Pull。origin/HEAD 等符号引用不是可创建为普通本地分支的目标。

<a id="section-05-04"></a>

### 删除不再需要的本地分支

**前提：** 确定分支已不再需要；重要提交有其他分支或备份引用承接。

1. 右键非当前本地分支，选择 Delete Branch…。
2. 核对分支名和警告；不确定是否含独有提交时先取消并检查历史。
3. 确认后检查分支列表与当前分支。

**结果：** 目标本地分支引用被移除，当前分支保持明确。

**注意：** 当前分支和被其他 工作树 占用的分支会受到限制。删除远程分支是另一项会影响协作者的操作。

<a id="section-05-05"></a>

### 安全查看旧版本

**前提：** 目标是一个旧 Commit，且不准备直接在无分支状态下工作。

1. 双击旧 Commit，或在 Commit 右键菜单选择“创建分支并切换…”。
2. 若已有本地分支直接指向目标，按提示选择该分支；否则填写一个新分支名。
3. 核对固定起点并创建、切换，再查看文件。

**结果：** 在有名称的分支上检查旧版本，后续提交有明确归属。

**注意：** 直接进入 Detached HEAD 默认关闭，Commit 菜单中的直接切换选项置灰并提示需要创建分支。Commit 顶端有本地分支时，菜单明确显示切换到该分支或选择分支。若主动启用高级选项，后续新提交仍需新建分支承接，原分支位置不会自动跟随。

**排错：** 发现自己已处于 Detached HEAD 时，先为需要保留的新提交创建分支，再切换回原分支。

<a id="chapter-08"></a>

## 远程协作

Fetch 更新本机知道的远端状态；Pull 把远端改动整合进当前分支；Push 把本地提交发送到目标远端。先区分这三个动作，再检查来源和目标。

<a id="section-08-01"></a>

### 添加远端

**前提：** 已取得正确的远端仓库 URL 或本地 Git 远端路径；联网服务所需的认证方式已准备好。

1. 在 Remotes 标题点击 Add Remote… 加号，或使用同名右键入口。
2. 在 Remote Name 填写名称，例如 origin；在 Repository URL 填写你自己的远端地址。示例占位地址不是实际仓库。核对目标属于预期项目后点击 Add Remote。
3. 完成添加后查看 Remotes，必要时 Fetch 获取引用。

**结果：** 远端出现在导航中，可以获取远程分支。

**注意：** 不要把访问令牌或密码写进说明、提交信息、截图或不可信 URL。

**排错：** 认证失败时使用托管服务与 VS Code 支持的认证流程处理，不要反复修改仓库内容来试错。

![图 25  填写 Remote Name 与自己的 Repository URL 占位示例不是实际仓库](images/user-manual/figure-25.png)

<a id="section-08-02"></a>

### 获取远端更新并拉取

**前提：** 已连接远端；准备 Pull 时，当前分支与本地修改状态已确认。

1. 对目标 Remote 执行 Fetch，等待结果栏报告成功。
2. 查看远端分支和历史差异，理解即将整合的提交。
3. 需要更新当前分支时使用 Pull。在 Remote 可选字段和当前 upstream 信息中核对来源；在 Pull Strategy 选择符合协作约定的策略。只允许快进时使用 Fast-forward Only。
4. 成功后检查历史；若产生冲突，按“合并与冲突处理”完成或中止操作。

**结果：** Fetch 后远端引用更新；Pull 后当前分支已整合目标改动，或明确进入待处理状态。

**注意：** Graph 的“已在远端”状态以最近一次 Fetch 后本机知道的远端引用为依据，并非实时查询服务器。

![图 26  Pull 对话框中的 Fast forward Only 策略](images/user-manual/figure-26.png)

<a id="section-08-03"></a>

### 推送本地提交

**前提：** 当前处于明确的本地分支；要发送的提交已完成检查。

1. 点击 Push，阅读实际的 Local Branch → Remote/Remote Branch。
2. 若没有远端，按说明进入 Add Remote… 完成连接，再返回 Push。
3. 首次 Push 时留意建立 upstream 的说明；多远端且目标无法确定时明确选择远端。
4. 需要改变目标时使用 Change Target…，再次核对来源、远端与目标分支。
5. 执行 Push，等待成功反馈，并检查未推送数量是否按实际情况更新。
6. 结果栏默认单行显示状态、结果摘要和操作图标；展开“操作详情”查看各目标的发布或更新状态、远端链接的打开／复制入口和完整输出。多目标部分成功时先核对每个目标，不要直接重试。
7. GitHub/GitLab 可从结果或分支右键菜单进入 PR/MR 创建页；没有远端直接链接时，在 AlwayGit 前端浮窗确认目标仓库和分支，再前往网页完成创建。GitHub 的目标仓库可以选择 Fork 的上游仓库；GitLab Fork 需要远端提供的 MR 链接。入口不会自动提交 PR/MR，且不代表已查询现有 PR 或 CI。已推送 GitHub 标签可进入 Release 创建页。

**结果：** 目标远端分支收到预期提交，或出现明确的失败原因。

**注意：** Push 角标表示尚未推送的数量，不是错误数量。Detached HEAD 下工具栏 Push 不可用。普通 Push 默认只推送分支，并显式使用 `--no-follow-tags`，不会受本机 `push.followTags` 配置影响；如需同时推送指向已推送提交的 annotated Tag，可在高级选项勾选“同时推送相关的 annotated Tag”。该选项可以仅用于本次操作，也可以勾选“记住为默认”持久化到设置；lightweight Tag 和无关 Tag 仍需通过 Tag 的 Push 操作显式推送。

**排错：** 被拒绝时先 Fetch 并检查分叉、认证与权限。不要把 Force-with-lease 当成常规重试。

![图 27  首次 Push 明确 feature/release → origin/feature/release 并建立 upstream](images/user-manual/figure-27.png)

<a id="section-08-04"></a>

### 谨慎使用 Force with lease

Force-with-lease 位于 Push 的高级选项中，用于已经决定改写远端历史的情形。它只在远端未发生未知变化时提供保护，并不等于“不会影响别人”。使用前与协作者确认，保留备份引用，理解要替换的历史。不能确定时取消，先 Fetch 和比较。

<a id="section-08-05"></a>

### 远程分支删除

远程分支的 `Delete Branch from <remote>…` 会改变服务器上的引用。单项或同一 Remote 的多选删除都应逐项核对远端与分支清单，并阅读二次确认；部分失败时按结果逐项处理。origin/HEAD 等符号引用不能作为普通分支删除。

<a id="chapter-07"></a>

## 临时保存和恢复修改

Stash 用于暂时保存尚未提交的修改。它与 Stage 完全不同：Stage 准备提交，Stash 保存并腾出工作区。恢复时先用 Apply 保留原条目，确认无误后再决定是否删除。

<a id="section-07-01"></a>

### 保存全部修改

**前提：** 希望暂时收起当前工作内容；知道是否需要包含未跟踪文件。

1. 使用顶部工具栏或 Stashes 标题的 Stash All Changes…。
2. 填写便于识别的说明，按需要勾选包含未跟踪文件。
3. 确认保存范围后执行，阅读保存文件数、未跟踪文件数和操作后状态。
4. 在 Stashes 中找到新条目，检查其内容。

**结果：** 选定范围被保存为 Stash；工作区状态与反馈一致。

**注意：** Include untracked files 不包含被 .gitignore 忽略的文件；未勾选时，也不会保存普通未跟踪文件。Stash 不能替代完整项目备份。

![图 21  保存全部修改前检查 Include untracked files 勾选范围](images/user-manual/figure-21.png)

<a id="section-07-02"></a>

### 只保存所选文件

**前提：** 使用 Git 2.43 或更新版本；只想临时保存并收起某些完整文件，其他文件应保持原状。

1. 在 Working Tree 选中目标文件，可跨 Staged 与 Unstaged 选择。
2. 右键已选文件，选择 Stash Selected Files…。
3. 核对去重后的文件数、完整路径与说明，确认后保存。
4. 查看未选文件仍保留原状，并检查新 Stash 的文件分类。

**结果：** 明确选中的整个文件被保存，同一文件只计一次；未选文件不应被顺带清理。

**注意：** 即使从 Staged 一侧选择，也会保存该文件完整的 Index 与 Working Tree 状态，不是只保存你看到的那一侧。

![图 22  所选文件 Stash 同时保存完整 Index 与 Working Tree 状态](images/user-manual/figure-22.png)

<a id="section-07-03"></a>

### 查看并恢复 Stash

**前提：** 使用 Git 2.43 或更新版本；当前仓库、分支正确。先检查并妥善保存其他工作，建议在干净现场恢复。

1. 右键 Stash 选择 View Changes，按实际出现的页签查看 Working Tree、Index 和 Untracked Files 分类及数量。
2. 优先选择 Apply Stash，在恢复后保留原条目；只有明确需要成功后删除时才选择 Pop Stash。
3. 在确认对话框核对 Stash 描述和目标仓库，再点击 Apply Stash 或 Pop Stash。
4. 若预检通过，等待恢复结果，并检查 Staged 与 Unstaged 分布。
5. 确认文件内容正确，再决定是否删除已不再需要的 Stash。

**结果：** 保存的文件状态恢复到当前工作目录；Apply 保留条目，Pop 只在成功后删除。

**注意：** 恢复会尝试保留原 Index 状态。不要把 Stash 当成远端备份；条目属于本地仓库。

**排错：** 出现受阻说明时先处理路径占用或冲突，再关闭对话框并重新尝试，触发新的预检。

![图 23  所选文件 Stash 的 Index 页签 显示保存的暂存版本与对应 Diff](images/user-manual/figure-23.png)

<a id="section-07-04"></a>

### 处理 Stash 恢复受阻

**前提：** Apply 或 Pop 报告无法安全恢复。

1. 阅读受阻原因及 Git details；Show Log 提供同一份底层诊断。“冲突文件”是已确认的冲突路径，“恢复涉及文件”仅表示存档影响范围，不能据此认定它们就是阻碍路径。
2. 使用比较入口查看 Stash 保存的内容与当前文件；必要时打开当前文件。
3. 检查当前其他 Staged 和 Unstaged 文件。必要时先 Commit、另存 Stash 或可靠备份，让恢复现场干净；不要为了重试而丢弃现有内容。
4. 处理阻碍后，关闭对话框并重新选择 Stash 执行恢复。

**结果：** 恢复前置条件已澄清，或者安全地停止恢复并保留原 Stash。

**注意：** 预检受阻会停止整次恢复；正式执行后若遭遇新的外部修改或写入错误，不应假定现场一定完全未变。始终检查实际结果。

![图 24  Pop 在预检受阻时停止恢复并保留原 Stash](images/user-manual/figure-24.png)

图中是旧版受阻提示。当前版本会区分已确认的冲突文件与恢复涉及文件，并在 Git details 中显示具体诊断。

<a id="section-07-05"></a>

### 删除不再需要的 Stash

**注意：** Drop 不提供常规撤销，先确认保存内容无需保留。删除前不能只凭 stash 序号判断身份；其他保存或删除动作可能改变序号。

**前提：** 已确认内容不需要恢复，或已完整恢复并检查。

1. 右键目标 Stash，选择 Drop Stash…。
2. 核对条目说明及身份，再确认删除。

**结果：** 目标条目从 Stashes 列表移除。

<a id="section-07-06"></a>

### Stash 隔离恢复的支持边界

所选文件 Stash 保存和 Apply / Pop 隔离恢复要求 Git 2.43+。稀疏检出、受影响的子模块、活动外部 filter、自定义或默认外部 merge driver、不支持的文件类型等可能使现场无法准确复现而受阻；单文件超过 32 MiB 或本地快照累计超过 128 MiB 也会停止。现场检查可能受非所选文件影响。

这些是 AlwayGit 隔离试验的边界，不等同于 Git Stash 的全部能力。遇到边界时先保留现有修改和 Stash，按具体提示处理；不要为了绕过保护而直接丢弃内容。

<a id="chapter-06"></a>

## 合并与冲突处理

冲突处理的目标是得到正确的最终文件内容。“标记并暂存”只告诉 Git 文件已被处理，不会替你判断逻辑是否正确。

<a id="section-06-01"></a>

### 把另一个分支合并到当前分支

**前提：** 已切换到接收改动的目标分支；当前修改已保存，必要时有备份分支。

1. 确认当前分支是合并的接收方。
2. 右键提供改动的本地或远程分支，选择 Merge…。
3. 在对话框再次核对来源与当前目标分支，确认合并。
4. 成功时查看历史；发生冲突时转到下方冲突处理流程，不要再次发起 Merge。

**结果：** 成功合并或明确进入进行中状态；结果栏说明实际结果。

**注意：** “右键哪一个分支”表示合并来源，当前分支是被更新的目标。

![图 17  将 feature/guide 合并进当前 main 核对方向后执行](images/user-manual/figure-17.png)

<a id="section-06-02"></a>

### 手动解决冲突

**前提：** 工作台显示进行中的 Git 操作，或存在 Conflicts 文件。

1. 点击操作条的“查看冲突”，进入 Working Tree 并定位冲突文件。
2. 底部 Ours / Theirs 仅供只读比较。点击冲突文件旁的铅笔，在 VS Code 打开文件，理解两侧改动并编辑成要保留的完整结果。
3. 清理不应保留的冲突标记并保存文件。必要时检查相关文件并运行项目自己的验证。
4. 回到 AlwayGit，选择已经处理好的冲突文件，执行 Manually handled: Mark & Stage（已手动处理，标记并暂存）；无单项选择时，All 按钮处理所有冲突文件。
5. 检查 Staged Diff，确认暂存的是刚刚保存的结果。对其他冲突文件重复处理。

**结果：** Git 的未合并条目归零，操作条进入“待检查结果”；仍需人工确认内容正确。

**注意：** 不要将普通 Stage 与冲突标记暂存混用。保存编辑器内容后，还必须重新暂存，Index 才会更新。

**排错：** 若选错内容，先继续编辑并保存，再次暂存并检查；不要把“冲突数为零”当成验证通过。原生编辑提示 Trust the project workspace 时，按第 11 章处理目标窗口的信任状态。

<a id="section-06-03"></a>

### 检查暂存结果并继续

**前提：** 所有冲突已按预期处理，Staged 结果已经复核。

1. 点击 Continue 或活动操作中的普通 Commit。
2. 阅读暂存检查列表，检查疑似冲突标记的位置和未扫描文件。
3. 有问题时返回检查，通过暂存 Diff 或编辑入口修正；修改后保存并重新 Stage。
4. 检查没有问题时，点击 Confirm & Continue（确认并继续）。
5. 若有疑似标记或未扫描文件，只有明确核对后才勾选必要确认并使用“仍然继续”；否则选择 Return to Review 返回检查。
6. 操作完成后确认活动操作条消失，并检查历史与 Working Tree。

**结果：** 进行中的操作真正完成，结果内容经过你的检查。

**注意：** 检查有大小、二进制、编码和子模块边界。没有疑似标记也不保证语义正确；检查后 Index 或分支变化会要求重新检查。

<a id="section-06-04"></a>

### 中止一次进行中的操作

**前提：** 确定不再继续本次 Merge、Rebase、Cherry-pick 或 Revert。

1. 在持续显示的操作条或处理对话框中选择 Abort 或“中止本次操作”。
2. 阅读起始提交与恢复说明；如需保留手动处理内容，先可靠备份。
3. 通过工作台说明和原生确认后，再检查当前分支、历史与文件状态。

**结果：** Git 尝试恢复操作开始前的状态，进行中提示消失。

**注意：** 关闭处理窗口只关闭窗口，不会中止 Git 操作。Abort 可能丢弃冲突处理修改；操作前已有修改可能影响完整恢复。

**排错：** Abort 失败时停止重复写操作，保留错误信息，检查实际 Git 状态后再处理。

![图 20  Abort 显示起点和恢复风险 关闭窗口并不中止 Git 操作](images/user-manual/figure-20.png)

<a id="chapter-09"></a>

## 整理提交历史

这一章的操作应在理解历史关系后使用。执行前记录当前分支与提交，创建备份分支，清理或保存未提交修改。已共享历史尽量使用可审查的新提交来修正。

<a id="section-09-01"></a>

### 创建、推送和删除 Tag

**前提：** 明确要标记的版本。

1. 右键目标 Commit 或分支选择 Create Tag…，或使用 Tags 标题入口。
2. 在 Tag Name 输入名称，例如 v1.1.0；核对 Target Commit。需要说明时填写 Annotation。若希望立即发布，勾选“创建后推送此标签”并选择 Remote；该选择可以仅用于本次操作，也可记为默认。
3. 在 Tags 中检查新标签，使用 Locate Tag Commit in Graph 定位，或使用 Show Only This Tag History 查看标签历史。
4. 要发布标签时，右键单个或多选 Tag，选择 Push Tag… / Push N Tags…，核对完整标签清单和 Remote 后执行。
5. 删除本地标签时，右键目标 Tag 选择 Delete Tag…，核对名称后确认。

**结果：** 本地 Tag 指向指定版本、明确选择的 Tag 已发布到 Remote，或目标本地 Tag 被移除。

**注意：** 创建后推送会先保留本地 Tag；远端失败时可稍后通过 Push Tag 重试。Tag Push 只发送对话框列出的标签，支持轻量和注解 Tag，不会附带其他本地 Tag，也不会覆盖远端身份不同的同名 Tag。本地删除不会删除远端 Tag；本版本不提供远端 Tag 删除或替换。

![图 28  Tag Name 与 Target Commit 确定版本 Annotation 为可选说明](images/user-manual/figure-28.png)

<a id="section-09-02"></a>

### 把指定提交应用到当前分支

**前提：** 当前分支是接收方；工作区已准备好；理解目标提交的内容和依赖。

1. 先切换到接收改动的分支。
2. 在 History 中右键要应用的普通 Commit，选择 `Cherry-pick to <当前分支>`，例如 Cherry-pick to main。
3. 若是 Merge Commit，单独操作并选择 Mainline Parent，先理解相对于哪个父提交取差异。
4. 批量时明确多选需要的真实 Commit，再执行批量 Cherry-pick；按拓扑列表从旧到新应用。
5. 成功后检查新增提交；冲突时处理并 Continue，或 Abort。

**结果：** 目标改动以新的提交进入当前分支，或明确暂停等待处理。

**注意：** 当前 HEAD 和当前分支历史中已有的提交会将普通 Cherry-pick 入口置灰，并显示原因；多选中包含这些提交时整体禁用，请先取消选择。其他普通 Commit 在关系检查通过后可直接执行，点击前就要确认目标。包含 Merge Commit 的批量选择不支持批量 Cherry-pick。若历史提交的改动曾被撤销或移除，可选择 `重新应用历史提交…`（英文界面为 `Reapply Historical Commits…`），勾选明确确认后执行；当前 HEAD 不提供此入口，重新应用仍可能产生冲突或空结果。

![图 29  Commit 菜单明确 Cherry-pick to main 此动作会应用到当前分支](images/user-manual/figure-29.png)

<a id="section-09-03"></a>

### 用 Revert 抵消普通提交

**前提：** 目标是普通 Commit；希望保留既有历史，并用新提交撤销目标的影响。

1. 切换到要修正的分支，检查目标 Commit 是否属于相关历史。
2. 右键目标 Commit，选择 Revert…。
3. 核对目标与确认信息后执行；若出现冲突，手动处理并检查暂存结果。
4. 完成后查看新增的反向提交与文件内容。

**结果：** 出现一条抵消目标影响的新提交，旧提交仍在历史中。

**注意：** Revert 不等于直接恢复整棵仓库到该提交，也不保证与之后改动自动兼容。Merge Commit 需明确 Mainline Parent；不清楚父版本含义时先取消，避免抵消错误范围。

![图 30  Revert 核对提交 ID 普通提交不需要 Mainline Parent](images/user-manual/figure-30.png)

<a id="section-09-04"></a>

### 将当前分支 Reset 到指定提交

**注意：** Hard 可能丢失未提交内容。Reset 已分享历史会影响协作，不应未经协调再强推远端。

**前提：** 理解会移动当前分支；已有备份引用，未提交内容已可靠保存。

1. 确认当前分支确实是要重置的分支。
2. 右键目标 Commit 选择 Reset…。
3. 在对话框中核对目标与模式：Soft 保留 Index 与工作文件；Mixed 重置 Index 并保留工作文件；Hard 同时重置工作文件。需要以后默认使用当前模式时，勾选“将此重置模式记为默认”；也可在设置 → 高级 → Git 操作中修改默认值。
4. 阅读全部警告，只有模式与意图完全一致时才执行 Reset；若出现 VS Code 原生 Proceed 确认，再核对目标后继续。
5. 检查当前分支指向、Staged 和 Unstaged，确认实际结果。

**结果：** 当前分支移动到目标提交，Index 与工作区按所选模式处理。

**排错：** 误操作后停止进一步修改，优先从备份分支恢复。Git reflog 可能帮助找回旧提交，但不能保证找回未提交文件内容。

![图 31  Reset 必须同时核对 Target Commit 和 Reset Mode 此处是 Soft](images/user-manual/figure-31.png)

<a id="section-09-05"></a>

### 执行普通 Rebase

**注意：** 本版本是普通 Rebase，不提供交互式重排、Squash 或 Fixup。

**前提：** 当前分支是要重放的分支；其提交尚未被他人依赖，或已完成协作约定。

1. 切换到要整理的分支，并为当前位置建立备份分支。
2. 右键新的基础分支，选择 Rebase…。
3. 核对当前分支和新基础，确认开始。
4. 冲突时逐步解决、暂存并 Continue；只有明确要丢弃本次正在重放的提交时才考虑 Skip。
5. 完成后核对提交内容和历史关系；不符合预期时按实际状态选择恢复方案。

**结果：** 当前分支的提交被重放到新基础上，提交 ID 可能变化。

**排错：** 进行中可以 Abort；完成后的恢复应使用事先保存的备份引用，避免未经检查地继续改写。

![图 32  Rebase feature/guide onto main 新基础为 main 提交 ID 会变化](images/user-manual/figure-32.png)

## 仓库和项目分组

先选择“操作对象”，再明确“当前工作仓库”。蓝色选中行表示准备操作的对象；仓库图标的强调色表示当前仓库；工作树 和本地分支前的实心三角形表示当前项。两者可以不同。Repositories、Local Branches、单个 Remote 和 Worktrees 之间同时只保留一个蓝色操作选择作用域；转到另一类对象时会清除上一类的蓝色选择，但不会改变当前仓库、当前分支或 Graph 勾选。

<a id="section-02-01"></a>

### 添加单个仓库或批量发现

**前提：** 目标目录已经是 Git 仓库，或包含若干 Git 仓库；你拥有读取这些目录的权限。

1. 点击 Repositories 标题右侧的 Add… 加号，选择“添加仓库”。
2. 选择一个仓库目录，或一个存放多个项目的父目录。
3. 等待扫描。在结果中核对仓库名称、可添加与已添加状态；按需筛选、取消勾选或选择连续范围。
4. 选择目标分组，必要时在同一流程中新建分组。检查主按钮显示的添加数量后确认。
5. 在导航中双击新添加的仓库，或让仓库行获得焦点后按 Enter。

**结果：** 选定仓库出现在导航中；已有仓库不重复添加。只有最后确认的仓库被登记。

**注意：** 扫描找到一个有效仓库后不会继续扫描其内部，因此不会顺带发现嵌套仓库或子模块。关闭或取消扫描不会部分添加。

**排错：** 无法访问的目录会被跳过；查看扫描结果中的原因，确认路径与权限后单独重试。

![图 05  Add Repository 与 Add Group 位于同一添加浮窗 通过 Choose Folder 选择目录](images/user-manual/figure-05.png)

<a id="section-02-02"></a>

### 创建和整理项目分组

1. 在 Add… 浮窗切换到“添加分组”，输入名称并创建。
2. 右键一个或多个仓库，选择 Move to Repository Group…，再选择目标分组。
3. 通过分组标题展开或收起内容。需要调整顺序时，使用同层拖动或右键的上移、下移。
4. 右键分组可重命名或删除；删除前阅读确认说明。

**结果：** 仓库按你的项目分类排列；删除分组后，其仓库回到根层。

**注意：** 分组只组织导航，不移动磁盘目录，也不会合并不同仓库的内容。

![图 06  learning labs 分组和其中四个示例仓库 atlas-project 示例仓库的当前状态标记](images/user-manual/figure-06.png)

<a id="section-02-03"></a>

### 选择对象并切换仓库

**前提：** 确认目标仓库已添加。

1. 单击仓库名称只选择操作对象。按 Ctrl（macOS 为 Cmd）逐项增减选择，按 Shift 选择可见连续范围。
2. 需要真正切换当前仓库时，双击目标仓库，或选中后按 Enter。
3. 切换后查看当前仓库图标、分支名与 Working Tree，再进行写操作。

**结果：** 工作台显示目标仓库的历史和文件状态；单击的批量选择不会被误认为切换。

**注意：** 仓库范围中的 Ctrl/Cmd+A 全选逻辑仓库；Escape 清空操作选择。输入框中的快捷键仍用于编辑文字。

<a id="section-02-04"></a>

### 从导航移除仓库

**前提：** 只是不想继续在 AlwayGit 列表中显示该仓库。

1. 右键一个仓库或已选中的多个仓库，选择 Remove from AlwayGit…。
2. 阅读确认浮窗中的完整仓库清单，确认后移除。

**结果：** 仓库不再显示于 AlwayGit 导航；磁盘文件和 Git 数据保持在原处。

**注意：** “从 AlwayGit 移除”与“删除磁盘目录”不是同一件事。移除当前仓库后，工作台回到未选择状态。

**排错：** 需要重新显示时，明确执行 Add… 再次添加原目录。

<a id="section-02-05"></a>

### 在新标签或项目窗口打开

**前提：** 先确认准备打开的仓库或 工作树。

1. 并排查看项目时，右键仓库并选择 Open in New AlwayGit Tab。
2. 需要编辑该项目时，使用 Open Repository in New Project Window 或顶部 Open in VS Code。
3. 需要空白的独立工作台窗口时，使用启动侧栏的 Open Workbench in New Window；进入后自行选择仓库。

**结果：** 新标签保存自己的查看位置；项目窗口用于原生文件编辑。

**注意：** 多个标签的查看状态独立，Git 仓库本身仍共享。并发写操作和外部工具修改都可能影响其他视图。

<a id="chapter-10"></a>

## 同时使用多个工作目录

工作树 让同一仓库拥有多个工作目录，用于同时处理不同分支。它们共享 Git 存储和部分引用，但各自的文件、Index 与提交草稿需要分别检查。

<a id="section-10-01"></a>

### 添加 工作树

**前提：** 已选择所属仓库；准备一个合适的新工作目录和未被占用的分支。

1. 在 工作树 标题点击 Add 工作树…。
2. 在 工作树 Folder 填写新工作目录，或用 Browse 选择；避免误用已有项目目录。
3. 使用现有分支时，在 Existing Branch 中选择尚未被占用的分支；新建时将其设为 None，在 New Branch 输入名称，并核对 Start Point。
4. 核对路径和分支占用提示，确认创建。
5. 在 工作树 中找到新目录，双击或按 Enter 切换进去。

**结果：** 新工作目录出现于当前仓库的 工作树 中；顶层 Repositories 仍按同一仓库归并。

**注意：** 默认不允许创建 Detached 工作树。不要把独立克隆与 linked 工作树 混为一谈。

![图 33  Add 工作树 中的新分支与起点设置 此图聚焦分支选项](images/user-manual/figure-33.png)

<a id="section-10-02"></a>

### 切换或在项目窗口打开 工作树

1. 单击 工作树 只选择操作对象；双击或 Enter 才切换当前工作目录。
2. 确认当前 工作树 三角形、分支和 Working Tree 文件状态。
3. 需要在独立 VS Code 项目中编辑时，右键选择 Open 工作树 in New Project Window。

**结果：** 工作台和编辑窗口对应正确目录；修改不会被误认为属于另一工作目录。

**注意：** 同一仓库的多个 工作树 显示为一个逻辑仓库入口，但文件状态与 Index 不会合并。

<a id="section-10-03"></a>

### 移除不再需要的 工作树

**注意：** 这会移除目标 工作树 的实际工作目录；强制移除可能丢失未提交文件。它与“从 AlwayGit 导航移除仓库”不同。主目录、当前目录及锁定状态均可能阻止移除。

**前提：** 目标不是主 工作树，也不是当前 工作树；其修改已保存。

1. 先切换到其他工作目录。
2. 右键目标 工作树，选择 Remove 工作树…。
3. 核对目录、锁定原因与确认信息。不要为绕过未提交内容保护而随意勾选 Remove even with uncommitted changes。
4. 点击 Remove 工作树；若出现原生 Proceed 确认，再次检查目录后继续。
5. 确认后检查 工作树 列表与磁盘结果。

**结果：** 目标 工作树 的目录被移除；分支引用仍可保留，需另行管理。

<a id="chapter-11"></a>

## 设置和常见问题

<a id="section-11-01"></a>

### 设置语言和阅读外观

1. 点击右上角齿轮，进入设置。
2. 在常规、界面、提交图或高级分组选择具体页面。
3. “界面 → 字号与密度”集中调整界面字号和提交列表密度；“界面 → 文件列表”调整分栏或统一显示方式以及文件间距；“界面 → Diff”集中调整 Diff 字号、行高和导航范围，并提供代码差异预览。导航的特殊规则可展开“详细规则”查看。
4. 点击“应用”保存；不想保留时点击“取消”、关闭或按 Esc。

**结果：** 语言、主题、配色、字号、密度、快捷键和阅读偏好保存在用户设置，并同步到同一配置环境的其他工作台窗口。取消只撤回当前窗口尚未应用的预览。布局尺寸、浏览位置和提交草稿分别恢复。

**注意：** 简体中文界面保留 Rebase、Cherry-pick、Graph、Stash、HEAD、Index 和 Diff 等核心 Git 术语；路径、分支名、用户内容和 Git 原始输出保持原文。


<a id="section-11-02"></a>

### 为什么文件或 Diff 打不开？

**前提：** 错误信息为 Trust the project workspace before opening it from AlwayGit，且你已核实项目来源可信。

1. 切换到目标仓库的 VS Code 项目窗口。它可能已创建，但因为信任检查失败而没有显示到最前。
2. 若没有该窗口，使用 File → New Window，再用 File → Open Folder… 打开目标仓库目录。
3. 在目标窗口运行命令 Workspaces: Manage Workspace Trust，或点击 Restricted Mode。只在确认可信后信任该项目目录。
4. 确认目标窗口使用同一 Profile 并已启用 AlwayGit，返回原工作台重新打开编辑或 Diff。

**结果：** 原生编辑或 Diff 在正确的受信任项目窗口中打开。

**注意：** 加入 AlwayGit 的仓库列表不等于已经信任该目录；无需为了一个项目信任其所有上级目录。

<a id="section-11-03"></a>

### 调整布局并恢复

**前提：** 希望在历史、详情与 Diff 之间重新分配空间。

1. 拖动面板分隔线，调整左侧、右侧和底部区域。
2. 拖动 Graph、作者和日期列的可见边界，按阅读需要调整列宽。
3. 使用 Diff 标题栏图标收起或恢复下方面板。
4. 布局不合适时点击 Restore Layout。

**结果：** 获得适合当前任务的阅读区；Restore Layout 恢复尺寸与 Diff 展开状态。

**注意：** Restore Layout 不负责清除语言、主题或提交草稿。

<a id="section-11-04"></a>

### 先看错误反馈再重试

结果栏会保留操作名称、目标与成功或失败状态。发生错误时，先展开完整错误，检查当前仓库与进行中操作条，再打开日志。切换仓库后，不要把另一个仓库的结果当作当前操作的结论。

| 现象 | 先检查 | 下一步 |
| --- | --- | --- |
| 仓库列表有蓝色选择但内容没切换 | 是否仅单击选择了对象 | 双击或 Enter，然后确认当前仓库图标 |
| 普通 Commit 不可用 | 是否有 Staged 文件、是否有冲突 | 检查暂存范围和操作条；仅改说明的 Amend 可无 Staged 文件 |
| 切换分支受阻 | 可能覆盖的文件、工作树 占用 | 保存修改或打开占用分支的 工作树 |
| Push 失败 | 目标、认证、权限、远端是否前进 | 先 Fetch 和比较，再按错误处理 |
| Diff 内容不完整 | 是否二进制、编码异常或预览截断 | 使用原生 Diff 或编辑器 |
| 没有提交图连线 | 是否正在搜索或没有勾选引用 | 清空搜索或调整引用范围 |

<a id="section-11-05"></a>

### 环境和支持边界

基础功能要求 VS Code 1.95+ 与 Git 2.40+；所选文件 Stash 保存和 Apply / Pop 隔离恢复要求 Git 2.43+。在远程宿主使用时，也要检查该宿主中的 Git 版本。

Git 在仓库所在的 VS Code 扩展宿主中执行。产品架构面向本地、WSL、Remote SSH 与 Dev Containers；不同环境仍需分别确认 Git、路径、权限和认证。未受信任工作区不执行 Git，纯浏览器虚拟工作区不受支持。

当前范围：整文件暂存、普通 Rebase、远程分支管理和显式 Tag 推送。当前不提供：分块暂存、交互式 Rebase、提交重排、Squash、Fixup、Format Patch、远端 Tag 删除或替换和自由浮动面板。

| 配置项 | 默认值或范围 | 说明 |
| --- | --- | --- |
| alwaygit.gitPath | 空；机器级 | 显式路径优先，否则使用内置 Git 扩展路径或 PATH |
| alwaygit.historyPageSize | 300；50–1000 | 每页加载真实 Commit 的数量上限 |
| alwaygit.refreshInterval | 15 秒；5–300 秒 | 可见工作台的补偿刷新间隔 |
| alwaygit.allowDetachedHead | false | 直接进入 Detached HEAD 的高级策略 |
| alwaygit.pushFollowTags | false | 普通 Push 默认是否附带相关注解 Tag |
| alwaygit.pushTagAfterCreate | false | 新建 Tag 后默认是否推送到所选 Remote |
| alwaygit.defaultResetMode | mixed | Reset 对话框默认选中的 Soft、Mixed 或 Hard 模式 |
| alwaygit.language | en / zh-CN / auto | 初始语言，工作台保存的选择优先 |

修改 Git 路径或刷新间隔后重新加载 VS Code 窗口。工作台内的主题、配色、字号、密度和语言在应用后即时生效。

## 随手查

<a id="section-12-01"></a>

### 选择和快捷键

单键快捷键默认开启，下表列出默认绑定；应用内帮助会显示当前有效绑定。焦点位于当前 AlwayGit 工作台内时，在仓库、History、文件列表、Diff、按钮或空白区域均可使用。文字输入框、文本域、可编辑内容、下拉选择控件、输入法组合、弹窗和右键菜单中暂停全局快捷键；离开工作台进入 VS Code 编辑器或终端后，由对应视图处理按键。长按不会重复触发操作。

| 按键 | 动作 | 范围与行为 |
| --- | --- | --- |
| R；Ctrl/Cmd+R | 刷新 | 刷新顶部当前打开的仓库 |
| F | Fetch | 与顶部按钮一致 |
| L | Pull | 打开 Pull 窗口 |
| P | Push | 打开 Push 目标确认窗口 |
| C | 准备 Commit | 打开 Commit 浮窗并聚焦提交信息，不直接提交 |
| S | Stash All Changes | 打开保存全部修改的窗口 |
| W | 查看 Working Tree | 查看未提交修改，不聚焦输入框 |
| H | 定位 HEAD | 沿用当前 HEAD 定位和历史范围规则 |
| O | 打开仓库文件夹 | 打开或切换到当前仓库的 VS Code 窗口 |
| D | Open Diff | 打开当前文本预览文件的原生 Diff；图片和二进制禁用 |
| E | 编辑文件 | 与当前“在 VS Code 中编辑”按钮一致；文本 Commit 比较打开原生 Diff，图片和二进制禁用 |
| [；] | 上一处；下一处修改 | 遵循 Diff 导航范围设置；折叠时先展开再跳转 |
| \ | 收起／展开 Diff | 保留阅读位置 |
| / | 搜索提交 | 聚焦并选中 Commit 搜索框内容 |
| , | 设置 | 打开 Settings |
| ?（Shift+/） | 帮助 | 打开帮助与指南 |
| A；U | Stage All；Unstage All | 分组模式仅在 Working Tree 可用，按筛选确认匹配范围；统一模式在任意详情视图确认完整仓库范围，忽略筛选和选择 |
| N | 新建内嵌终端 | 打开底部面板并以当前仓库根目录创建默认 Shell |
| T | 聚焦当前终端 | 当前为 Diff 时切换到最近创建的终端；没有终端时创建一个 |
| Ctrl+Alt+Shift+T；macOS Cmd+Alt+Shift+T | 新建内嵌终端 | VS Code 层命令，可打开工作台；当前无仓库时待选择仓库后创建 |

D、E、[、] 和 \ 仅在 Diff 标签活动时可用；终端输入区暂停工作台单键。全局操作以顶部当前打开的仓库和当前预览文件为目标，不随侧栏临时选择或鼠标悬停改变目标。按钮禁用时对应快捷键也不执行。A/U 的操作范围遵循上表中的列表模式，不随批量选择或分组折叠改变；所选文件操作使用原有右键菜单。

悬停相关按钮可查看当前绑定。Settings → 常规 → 快捷键提供搜索、分类和“仅显示已修改”筛选。点击按键录制替换绑定，或用加号增加备用键；每个动作最多两个绑定。按键旁的关闭图标移除单个绑定，禁用图标清空该动作的绑定，恢复图标恢复默认；顶部恢复按钮恢复全部默认。

录制框获得焦点后，按下单键或组合键；Ctrl/Cmd 自动按平台适配。Esc 仅取消录制，Tab 移至确认按钮。列表内冲突会显示占用动作，不能直接保存；明确选择“将绑定移至此处”会移除原动作的冲突绑定。恢复默认发生冲突时也需要确认移动。基础导航、选择和文字编辑键保留，输入法组合和 AltGr 不用于录制；不支持连续多段组合键。VS Code 或操作系统可能优先处理组合键，此页面无法完整检查外部冲突。

点击 Apply 应用并保存到用户设置，跨窗口共享；Cancel 恢复原绑定。关闭单键开关会暂停无修饰键及 Shift 加可打印字符的绑定，保留配置；其他组合键仍可用。默认 Ctrl/Cmd+R 可修改或禁用，原有选择操作保持不变；草稿、仓库选择和布局继续保留。独立的新建内嵌终端快捷键由 VS Code 管理，可通过页面中的“打开 VS Code 键盘快捷方式”入口修改。

| 动作 | 含义 | 范围提醒 |
| --- | --- | --- |
| 单击仓库或 工作树 | 选择操作对象 | 不切换当前工作目录 |
| 双击仓库或 工作树 / Enter | 真正切换 | 执行前后核对当前项 |
| 勾选引用 | 改变 Graph 范围 | 不 Checkout |
| Ctrl/Cmd + 单击 | 增减多选 | 右键已选项保留该范围 |
| Shift + 单击 | 可见连续范围 | 目录折叠会影响可见顺序 |
| Ctrl/Cmd + A | 全选当前焦点所属范围 | 输入框中仍全选文字 |
| Escape | 清除当前范围选择或关闭菜单 | 输入框保留原生行为 |
| Shift + F10 / 菜单键 | 打开当前对象菜单 | 方向键移动，Enter 执行 |
| History 恰好选两个 Commit | 自动 Compare Commits | Working Tree 不参加 Commit 多选 |

<a id="section-12-02"></a>

### 常用术语

| 术语 | 在这里的意思 |
| --- | --- |
| HEAD | 当前检出的版本；通常指向当前分支的最新提交 |
| Index / Staged | 下一次 Commit 准备保存的文件内容 |
| Unstaged | 磁盘相对 Index 尚未暂存的变化 |
| upstream | 本地分支跟踪的远程分支 |
| OID / Commit ID | Git 对象标识；短哈希便于阅读，完整 ID 用于精确引用 |
| Detached HEAD | 当前直接检出一个提交，没有附着到普通本地分支 |
| Merge Parent / Mainline Parent | 合并提交的父版本；选择不同父版本会改变比较或取用差异的含义 |
| 工作树 | 共享同一仓库 Git 存储的另一个工作目录 |

<a id="section-12-03"></a>

### 按目标查找操作

| 我想做什么 | 应该找的入口 |
| --- | --- |
| 把当前文件修改保存为版本 | Working Tree → Stage → Staged 检查 → Commit |
| 先放下修改去处理另一件事 | Stash All Changes 或 Stash Selected Files |
| 看看两个版本有哪些变化 | History 恰好选择两个 Commit |
| 把其他分支的完整进展整合进来 | 目标分支作为当前分支 → 右键来源 → Merge |
| 只拿某一条提交的改动 | 目标分支作为当前分支 → Commit 菜单 → Cherry-pick |
| 撤销已经共享的某个提交影响 | Commit 菜单 → Revert |
| 回到旧版本继续开发 | 旧 Commit → 创建分支并切换 |
| 同步服务器的新引用 | Remote → Fetch |
| 把本地提交发给协作者 | Push → 核对目标 |
| 同时编辑两个分支 | 工作树 → Add 工作树 |
