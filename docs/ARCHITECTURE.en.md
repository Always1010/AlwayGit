# Architecture and Development Conventions

[简体中文](ARCHITECTURE.md) | [Project home](../README.md)

This document maintains AlwayGit's runtime structure, code entry points, conventions across layers, and development workflow. Product behavior is defined by the [Workbench Specification](WORKBENCH_SPEC.en.md). Check methods and validation evidence are maintained in [Validation and Local Updates](VALIDATION.en.md). Collaboration requirements are defined in the [Project Rules (Chinese)](../AGENTS.md).

<a id="runtime-structure"></a>

## Runtime Structure

AlwayGit is a Workspace extension for VS Code. The React workbench shares one messaging boundary and can run in an editor WebviewPanel or an independent WebviewView. The Node.js host manages these instances and shares Git subprocesses, repository discovery, clipboard, window, and file operations. `workbench-launcher.ts` registers three views that retain their hidden contexts: the primary sidebar retains the `alwaygit.workbenchLauncher` identity, the secondary sidebar uses `alwaygit.workbenchAuxiliary`, and the panel uses `alwaygit.workbenchPanel`. The docked container IDs are `alwaygit-panel` and `alwaygit-auxiliary`, following VS Code's letters, digits, underscores, and hyphens restriction; view IDs and existing session keys remain unchanged. The secondary sidebar is registered through `viewsContainers.secondarySidebar`, available as a stable API since VS Code 1.106. Locations that have not been opened show a lightweight launcher page retaining two command URIs. Its independent browser script only receives ready, close, and save requests for location settings and does not connect to repository or Git RPC. Enabled views load the workbench when restored or explicitly opened. The gear in a native view title sends the location dialog message to the corresponding launcher or workbench according to the source viewId; the internal location icon follows the same flow. Open requests during loading are delivered after the script is ready. The launcher and full workbench reuse WorkbenchLocationsDialog. Apply saves the entire configuration once; the frontend synchronously unmounts the dialog and restores focus before sending the close message. The host consumes that source's one-time default location and opens it. Cancel neither writes settings nor opens a location. The primary sidebar view has no visibility condition and always retains a launch entry. The secondary sidebar and panel use the alwaygit.auxiliaryLocationEnabled and alwaygit.panelLocationEnabled contexts to control views.when; VS Code automatically hides empty containers. Startup and configuration changes update these contexts from normalized location settings without automatically focusing newly enabled locations. Hiding the source is deferred while its settings are being saved. After the dialog close message arrives, visibility conditions are updated and then the default location opens. Replacement of the launcher's host page is suspended until its dialog closes, preventing loss of the save response. Move, new-window, and explicit-open actions keep separate entry points. The Webview neither reads disk directly nor executes Git.

`alwaygit.workbenchLocations` atomically stores `enabled` and `default` in one user-level configuration object. When reading older configuration, the host removes duplicates and corrects an invalid default. Saving strictly validates that locations are unique, at least one location is enabled, and the default is enabled. When no valid new configuration exists, `alwaygit.openMode` remains compatible: the former editor value means editor tabs only; the former docked value means editor tabs and the sidebar, with the sidebar as default. The left/right side follows VS Code's primary sidebar position setting. Explicit opening calls the container's `resetViewContainerLocation` and the view's `resetViewLocation` commands to restore their native area, then calls `.focus`, avoiding a mismatch between remembered moved locations and the requested destination. Show and the status bar route only to the default location; explicit commands open the specified location. The editor can reuse an existing editor instance; each sidebar and the panel reuse their own location's instance. When the secondary sidebar or panel is unchecked, the native view disposal callback retains its session and terminal-owning instance in the host. Re-enabling reloads the page with that session and transfers terminal ownership without restarting the Shell. Extension shutdown releases them together. Unchecking the editor or primary sidebar only restricts subsequent opening. SessionWriter stores editor, primary sidebar, secondary sidebar, and panel state in `alwaygit.session`, `alwaygit.dockedSession`, `alwaygit.auxiliarySession`, and `alwaygit.panelSession` respectively. Drafts, queries, selections, and terminals are isolated per instance; interface preferences remain shared.

“New Tab with Current State” uses `captureWorkbench` with a random token to read the source instance's live session, temporary filters, commit selection, comparisons, and Diff revisions. Responses are restricted to their source and validated against the Schema. It always creates a new editor tab without modifying existing tabs or the source instance; initialization replaces the destination's old Webview state. The active terminal tab is not copied: processes, input, and replay remain with the source. A failed read or an unfinished Git operation preserves every instance's state. The native move command receives the selected view ID, and users can still move independent views to the primary sidebar, secondary sidebar, or panel.

During startup, the extension registers commands, panel restoration, and window communication early. Activation completion does not wait for built-in Git or repository scanning. The Git executable path is resolved on the first Git request through one shared initialization task: explicit configuration takes priority, followed by the built-in Git path, with PATH as fallback. Startup repository scanning runs in the background. Workbench panels are created and load their scripts first; repository-list, collection, and ordering requests share the initial scan's completion result. Catalog-related pickers, discovery, and mutation requests also wait for that task. Saved paths are validated with at most four concurrent checks, collected in their original order, and published once only after all checks finish and the catalog revision is still valid; incomplete catalog entries are not exposed individually. Frontend catalog state is independent of repository Snapshot loading, and background catalog refreshes preserve loaded content. Initial scan failure preserves the interface and allows later catalog requests to retry. Subsequent panel opening or showing does not repeat the scan; workspace changes, catalog synchronization, and explicit refresh still trigger the existing scanning flow. Startup does not automatically create an editor workbench tab; enabled sidebar and panel views load the workbench when restored.

`src/protocol` is the shared boundary between Webview and host. Requests associate responses by `id`; Zod validates methods and parameters at the host entry. The host publishes repository changes, operation activity, and repository selection events. It only accepts registered repositories and predefined methods; Git RPC accepts no arbitrary commands. Explicitly created embedded terminals provide a Shell input channel isolated by panel ownership. The Demo adapter maintains its example model independently and initializes data only on the first request in explicit Demo mode. The production bridge neither initializes example state nor reads Demo storage.

## Repositories, Refs, and History

Repository identifies a working directory, `commonDir` identifies shared Git storage, and `gitDir` identifies that working directory's private Git metadata. Multiple worktrees sharing storage share a write-operation queue while retaining independent HEAD, Index, and working-directory state. Write operations revalidate repository, ref, and worktree state before execution.

Git discovery identifies the main working directory by comparing the Git directory with the shared directory. Linked worktrees maintain optional `mainRoot` from the main directory returned by `worktree list`; ordinary repositories with independent storage still use their own working directory. Ownership is not inferred from the `.git` file type or remote URL. Shared pure functions in `src/protocol/repositories.ts` derive logical repositories from normalized `commonDir` for Workbench repository navigation; the active working directory remains the actual operation target. User-created Repository Collections form a separate display hierarchy and store membership by logical repository key. Repositories without a Collection appear directly at the root, without a special “Ungrouped” node. RepositoryManager and RPC retain the complete working-directory list and original path IDs, so saved paths, sessions, and drafts require no rewriting. Scan counts use logical repositories; adding a worktree publishes a list change even when the repository count does not increase.

Worktree Overview uses a separate cancellable read category and `worktreeOverview` RPC: inventory first, then status batches of at most three paths. Each path verifies its actual Git root and common directory, reads porcelain v2 and operation markers, and avoids History, Tags, Stash, or full Snapshots. Failures are isolated per tree; close/repository changes cancel reads, and file events invalidate the affected path. Explicit refresh updates other directories that have no watcher. The history region stays mounted while hidden, preserving Graph/File History and drafts.


Manual directory addition traverses asynchronously in `src/repositories/discovery.ts`, invokes Git validation only for candidate directories with a `.git` marker, and stops descending at a valid repository. Repositories and empty Collections are created through the same embedded Add dialog. For an empty Collection, the Webview submits a Zod-validated name; the host checks duplicate-name rules again before saving and broadcasting. The Webview obtains the scan root only through the native directory picker, then requests discovery with a panel-owned scan ID. The host publishes progress to that panel; closing the dialog or canceling the scan stops traversal. Discovery results are temporarily held in the host without registering watchers or writing state. The Webview shows candidates grouped by logical repository, already-added state, problems, and the target Collection. Final submission contains only the scan ID and selected keys. The host rechecks cached results and the Collection before batch deduplication, watcher registration, saving, grouping, and catalog-change publication; the Webview cannot submit arbitrary disk paths. Canceling the scan or closing the confirmation list registers nothing. Display order at the root and within each Collection is stored in the shared catalog snapshot; entries use Collection IDs or normalized logical repository keys. The host rechecks that ordering source and target exist and belong to the same level, accepting only insertion before or after the target. Temporarily inaccessible repositories retain their order position; explicit removal clears it. User-added paths, exclusions, Collections, membership, and order use the extension's `globalStorageUri/repository-catalog.v1.json` as the authoritative snapshot, containing schema and revision. A short OS loopback-port mutex keyed by normalized storage directory protects rereading, validation, and atomic replacement through a temporary file. Watcher preparation, transactions, and publication within one host use FIFO. Scans and the compatibility `globalState` mirror run outside the lock; mirror failure does not reverse committed operations. Addition, Collection creation, and grouping commit together. Unknown schemas or damaged files are preserved and reported. The window bridge tells other hosts in the same isolation domain to reread the authoritative file, rediscover paths, and release removed entries; stale scans cannot commit. Older `globalState` is migrated when the catalog is first created; older `workspaceState` is imported once per workspace while respecting current exclusions. The embedded Webview confirmation dialog submits only displayed logical repository keys. The host rechecks existence and busy state before removal; removal releases watchers, deletes saved paths and membership, and saves a logical-repository exclusion to prevent immediate restoration by workspace or built-in Git discovery. Explicit addition clears the exclusion. Startup restoration only revalidates saved paths and repositories provided by VS Code; it does not recursively rescan classification directories. Local paths do not participate in Settings Sync.

The same commonDir shares reference-counted Git metadata watchers. Ref changes are broadcast; HEAD, Index, and operation markers notify the owning worktree by gitDir. Working-directory watchers remain separate per directory and exclude Git metadata by repository-relative paths. Bounded batch Index queries preserve tracked paths in node_modules events; failed queries or an exceeded scope conservatively invalidate state. Shared watchers are released only when the last member is removed. Automatic discovery and synchronization across windows share scan tasks. Directory or removal-state changes invalidate old results; subsequent scans reread current roots to avoid restoring removed entries through stale results.

Status uses porcelain v2 with NUL separators and stores Index and working-directory status separately. History queries accept a set of full ref names, deduplicate input refs, and resolve at most four concurrently. Default refs directly use immutable Commit IDs from for-each-ref; only nested Tags require additional resolution. The first query fixes tips, and subsequent pages reuse those tips, avoiding duplicates or omissions when refs move between pages. Resolved tips are supplied to log/rev-list through standard input so ref counts do not exceed command-line limits. Multiple refs return the union of Git-reachable commits, with shared ancestors returned once. The graph algorithm carries pending lanes across pages; the virtual list renders only visible rows.

`src/git/file-history.ts` builds a separate read-only file index from real topology. Literal-path queries find candidate commits; NUL-delimited diff-tree batches of 128 parent edges iteratively discover rename paths. Each Parent maps file versions independently, tracing a pinned source version through history reachable from selected refs. Additions/copies disconnect prior identity and deletion ends that version, excluding independent same-name recreations. `fileHistory.graphParents` projects hidden commits exclusively for rendering; real `Commit.parents` remain authoritative for details, comparisons, and actions. Metadata reads batch 128 immutable OIDs; pagination and message search apply to matching records. Known remote refs determine publication status.

Completed indexes cache at most four entries and 50000 records in total for 60 seconds, keyed by repository, pinned tips, source path/revision, HEAD, and shallow boundaries. Failed/canceled reads are not cached. Each trace permits at most 4096 aliases and one million topology nodes or version states, and inherits Runner output/time budgets; exceeded limits fail rather than returning partial history. The optional per-view `fileHistory` session field remains compatible with v2; paging, displayed scope, Back records, and snapshot invalidation keys share the same file identity.

Overlapping Snapshot requests for the same working directory share the running query through the application coordinator. Writes and file events immediately advance the invalidation generation. Stale snapshot values and errors redirect to reads of the current generation; old tasks cannot publish stale content or delete newer tasks. Operation responses and compensation polling directly carry the Snapshot already read, which the frontend reuses. Different worktrees remain independent. The ref index caches name and OID queries by immutable refs arrays, reducing repeated scans in History rows and the sidebar. Nested-Tag resolution and remote-target queries in snapshots, and name validation for batch local/remote branch deletion, each run at most four concurrent Git queries per batch. Batch branches are deduplicated before validation, and results retain input order. This is a per-batch limit, not the extension's total subprocess count.

Search input uses a 200 ms debounce; input changes immediately invalidate old results. Automatic location stops after at most 20 pages or 10000 entries, preserves results, and allows manual continuation.

History, Details (including Stash and comparisons), and Diff previews replace obsolete requests by panel and category. Changing repositories or closing a panel also cancels old requests. The host read-only coordinator runs at most three query tasks. A task may contain parallel Git commands, so this limit is not the extension's total subprocess count. AbortSignal propagates through the read-only scope to runner. A canceled running task continues occupying its slot until known Git handles finish; failure also cancels and waits for parallel commands in the same scope. Cancellation authority is restricted to the source panel. Writes and operation-result checks do not enter this queue.

Frontend asynchronous requests use repository and request generations to ignore old responses arriving after repository changes, refreshes, or refiltering. Host Snapshots have monotonic versions; compensation refreshes identify actual changes with a fingerprint excluding the version field. File-watch notifications carry relative working-directory paths and Index-change markers. Both host and frontend debounces merge change scopes; overlapping Snapshot requests retain unconsumed scopes so further content changes to files already marked dirty are not missed.

Background and post-operation refreshes decide whether to reread History from OIDs of selected refs, HEAD, and all remote refs. Remote refs participate to update push markers; Stage/Unstage alone does not force History reloads. Manual Refresh still queries History again. Loaded Commit details are retained by repository, OID, and selected Parent; History queries do not reselect the same Commit. Merge Parent is saved as an optional session field compatible with existing version 2 sessions.

Workbench tabs check the current repository in the background only when transitioning from hidden to visible, preserving the existing display, selection, drafts, and scroll position. Focus changes while continuously visible do not trigger checks. Without file-invalidation notifications, compensation polling compares the new snapshot and also specifically revalidates selected dirty files in the visible Working Tree, allowing further edits with unchanged status markers to refresh. Historical and purely Staged comparisons do not participate in this compensation. While hidden, repository-catalog changes and current-repository file-invalidation scopes are merged in the host and delivered once when visibility resumes; unknown scopes still cause full invalidation. Repository lists are reread only when the catalog actually changes. Background reads of loaded lists and repositories do not enter initial-loading state.

<a id="project-windows-and-remote-hosts"></a>

## Project Windows and Remote Hosts

The extension retains `extensionKind: ["workspace"]`; Git, filesystem operations, and PTY run on the repository's host. VS Code converts local file URIs from remote extension hosts to the client. Repository and file entry points continue using VS Code APIs without constructing SSH addresses or assuming Windows paths. Blank workbenches use `vscode.newWindow` to inherit the current remote connection; repository windows use `vscode.openFolder`.

The window bridge maintains registrations in the host machine's temporary directory, isolated by extension storage URI, VS Code application directory, remote kind, and existing IPC scope. Within one scope, loopback communication reuses project windows. This does not change the isolation algorithm or write-lease directory. Simulated SSH unit tests verify requests and scope isolation; they do not establish acceptance of real SSH multi-window, Profile, and client combinations.

## Workbench State

<a id="bilingual-ui-resources"></a>

### Bilingual UI Resources

Text for the interface, menus, settings, host prompts, and application-owned errors is maintained centrally in `src/i18n/catalogs/*.json`, grouped by feature. Each record has a stable semantic key, `en`, `zh-CN`, usage `context`, and `review` status. Keep the key when changing wording; do not regenerate identifiers from the new text. `translated` means a distinct Chinese counterpart exists, `pending` means English is retained pending copy review, and `keep` means the original is retained under current terminology conventions. New records with identical text must explicitly select one of the latter two states. Status supports review and checks without automatically rewriting text. The Chinese interface translates ordinary actions and objects while retaining Rebase, Cherry-pick, Graph, Stash, HEAD, Detached HEAD, Index, and Diff. Worktree is consistently translated as “工作树”; Checkout is translated as “切换” according to context. Names, paths, code, user content, and raw Git output are not translated.

Code passes only keys and named parameters: React uses `useTranslation()`, non-component presentation uses `uiText()`, shared layers use `translate(language, key, parameters)`, and application-owned errors use `message(key, parameters)`. Counts, branch names, paths, and targets in full sentences use `{{name}}` parameters. When plural forms are needed, write language-specific `one` / `other` forms; `count` must be numeric. Split display fragments only when inline code or labels require separate styling. Where historical wording uses different parameter counts in the two languages, `omitParameters` explicitly records allowed omissions. Intentionally blank display fragments use `allowEmpty`. Check tools validate these exceptions too; they must not conceal newly introduced parameter mismatches.

`scripts/i18n.mjs` generates runtime entries and key/parameter types in `src/i18n/generated.ts`, plus `package.nls.json` and `package.nls.zh-cn.json` for VS Code static contributions. Generated files must not be edited directly; checks reject stale output. Runtime bundles contain only text; context and review status stay in source resources. i18next handles interpolation and plurals, with language bound per call rather than changing the shared engine's global language. Untranslated English plurals retain English rules. Native confirmations and request prompts use the source panel's language through asynchronous request context; other entry points use saved language and extension configuration. VS Code's command palette, Activity Bar, and setting descriptions follow VS Code's own display language independently of the workbench language selector.

`GitError` / `MessageError` retain English diagnostic messages with optional keys and parameters. RPC hides credentials before output and sending, and sends error codes, display messages, structured details, and redacted text descriptors. The frontend presents known descriptors in the current panel's language; older responses and unknown descriptors retain their original messages. Raw Git output, repository contents, names, paths, and user input remain unchanged. Offline manuals continue as the existing Chinese and English Markdown documents rather than runtime entries.

`npm run i18n:export` exports the review checklist to ignored `artifacts/copy-review.csv`, which can be opened in Excel. It contains stable keys, bilingual text, status, context, resource files, and current code-reference locations. Resources are the only editable source; the spreadsheet is a generated review view. Write review comments back to resources by key, then regenerate, check, and export; do not maintain a second independent glossary.

State is classified as follows:

- Repository data: Snapshot, History pages, Commit details, and Diff previews.
- Per-repository views: checked refs, ref-directory expansion, sidebar-section collapse, search, current Commit, file, Stash, active area, and Commit drafts.
- Interface preferences: language, theme, light/dark Graph palettes and mainline color, status colors, interface and Diff font sizes and line heights, file spacing, shortcuts, change-list mode, and Diff navigation scope.
- Panel layout: splitter sizes, collapse state, and table-column widths, restored independently per tab; the workspace retains the initial layout for new tabs.

Session Schema and inferred types are centralized in `src/protocol/session.ts`. Persistence subscribes only to relevant fields. Each tab immediately writes its own VS Code Webview state. Frontend saveSession requests are coordinated with a 200 ms debounce, one in-flight request, and the latest pending state. Closing the Commit dialog uses flushNow to immediately send pending state; after the in-flight write finishes, the latest draft is saved. The deduplication baseline updates only after a successful response; failures retry at most twice and show a prompt. The extension host serially saves active-tab state to `workspaceState` as the baseline for new tabs and compatibility restoration. Inactive tabs update only their own state and submit the baseline when reactivated. If this host-initiated synchronization fails, it only records an output log and does not retry automatically. Each tab calculates draft and view changes against its own last successfully saved state and merges the latest host baseline during serialized writes. Unchanged fields from older tabs do not overwrite newer state from other tabs; blank tabs retain existing repositories, drafts, and views. Tabs have independent active repositories and frontend selection state. The host targets responses and repository switching by request source, while repository changes and Git activity broadcast to all tabs. Compensation refreshes cover current repositories in all visible tabs and deduplicate by repository. Demo mode uses browser localStorage. Persisted data contains only interface state, without credentials, Git output, or file contents.

Version 2 sessions accommodate new settings through optional `appearance` and `diffNavigationScope` fields; the latter defaults to the entire Commit and is retained after host protocol validation. Older sessions without custom colors receive complete light/dark palettes from the current presets. Old Editor Focus migrates to Workbench, and the old default 26 px line height migrates to 24 px; other dimensions and drafts are retained. The Settings dialog uses an in-memory baseline for live preview, while persistence subscriptions still write the baseline. After Apply, `saveInterfaceSettings` saves user configuration and broadcasts it to windows and tabs. Cancel restores the latest applied preferences without overwriting refreshed repository data. `alwaygit.interfaceSettings` and `alwaygit.language` are user-level configuration; when absent, existing preferences migrate from older workspace sessions while preserving drafts and browsing state. Current user preferences take priority when restoring Webview state. Ordinary session saves maintain only restoration copies and do not write user configuration. Unapplied local previews remain during synchronization; Cancel uses the latest shared baseline. Virtual-list dimensions depend on actual font size and density. Advanced Git policies use separate VS Code configuration: `alwaygit.allowDetachedHead`, `alwaygit.pushFollowTags`, `alwaygit.pushTagAfterCreate`, and `alwaygit.defaultResetMode`. They are not stored in interface sessions. `operationSettings` / `saveOperationSettings` RPC supports explicit user/workspace scope and strictly validates complete settings. The settings page edits user defaults by default. User reads use inspect to exclude workspace overrides, and user saves do not overwrite workspace policies; operations always use current effective configuration. Empty windows reject workspace writes. “Remember as Default” in action dialogs without an explicit scope follows the current window's existing scope rules. Apply takes effect only after successful saving, and configuration changes broadcast to all workbenches. Push, Create Tag, and Reset dialogs read initial values from applied settings and write them back only when users explicitly select “Remember as Default” and submit. Ordinary saveSession cannot overwrite these policies.

Git operation feedback is stored in frontend memory by repository ID. Operation sequence numbers prevent older results from replacing newer operations; switching repositories displays only that repository's feedback. Errors and results are not saved in sessions. Writes affecting the current working directory use a frontend progress overlay that isolates all workbench background areas and existing dialogs and blocks keyboard events. It depends on the union of the local execution set and host busy state and remains until interface synchronization finishes. File batch selection is temporary state in the current file area, separate from the Diff preview target; changing areas or disappearing files triggers selection revalidation.

`action` responses wrap optional `snapshot`, structured Push `result`, and `refreshWarning`; the Webview remains compatible with older Snapshot responses. Network commands use `--progress` to force progress through pipes. `network-progress.ts` independently decodes UTF-8 and CR/LF updates on stdout/stderr, parses known phases, and coalesces publication every 150 ms. Each command's parser clears its timer on completion or failure. Live messages bind source panel, repository, and RPC request ID. The frontend matches by request, retains current progress while switching repositories, and ignores late messages after completion. Unknown output updates only activity time; complete lines are redacted before delivery to Output, and raw credentials never reach progress UI. Push/Tag Push use `--porcelain` in the write queue to record actual destinations and ref statuses. Failure still throws GitError and passes redacted `pushResult` through the error protocol, without treating partial success as full success. Snapshot failure after host execution completes does not reverse the Git result. `hosting.ts` handles hosting-platform address parsing, branch encoding, Fork comparisons, and remote-link validation; generated web addresses remain separate from credentials. `remoteLinks` reads only locally resolved Push URLs and remote HEAD, while `openExternal` strictly validates HTTPS and credential-free URLs. Results and links remain only in current in-memory feedback.

App, History, Sidebar, Details, and Diff subscribe to the state fields they use. Major panels use memo and stable callbacks; unchanged snapshot fields, selection lists, and repository summaries reuse references. Content refreshes do not rerun Working Tree's proactive selection logic. Local Diff loading, draft input, and operation feedback do not make unrelated panels recalculate through whole-Store subscriptions. Theme, font size, layout, and actual shared-data changes still update relevant areas.

Context menus retain stable target identities and source elements. After an action dialog opens, Git writes still resolve and validate refs, Stashes, or worktrees again in the host. Repository switching closes old menus and dialogs. Menus use standard `menu` / `menuitem` semantics and support focus movement, Enter, Space, Escape, and outside-click dismissal. Only scrolling the source element or its ancestors, window resizing, and explicit dismissal close a menu; automatic Diff location or scrolling another panel does not.

<a id="embedded-terminals"></a>

## Embedded Terminals

`BottomDock.tsx` combines a fixed Diff tab with multiple terminal tabs; `dock-store.ts` stores tabs and the active object for the current workbench runtime. Existing session `layout.diff` and `layout.diffCollapsed` values directly provide the entire bottom panel's height and collapse state, so dimensions, views, and drafts are neither migrated nor discarded. Diff controls register executable shortcuts only while the Diff tab is active; global keyboard protection recognizes terminal input areas. `TerminalView.tsx` lazy-loads xterm.js and FitAddon, updates colors with the theme, and sends visible columns/rows to the host.

`src/protocol/terminal.ts` defines terminal-specific validation and events. The host requires a trusted workspace and a real source panel. Creation accepts only registered repository IDs, limited Shell options, and dimensions, without arbitrary paths or command startup arguments. `TerminalSessions` isolates sessions by source panel, checks ownership for input, close, resize, rename, snapshot, and output acknowledgments, retains descriptions after exit, and releases all sessions when their panel is disposed. Terminals are an explicitly open Shell input channel. They do not use Git RPC's action allowlist, confirmations, or write leases, and terminal output is not broadcast to other workbenches. New and restarted Shells create independent AskPass bridges in the extension host and reuse VS Code GitHub sign-in through shared `git-authentication.ts`. Each inquiry obtains the session again so long-lived terminals do not retain expired tokens. This respects `git.useIntegratedAskPass` and `git.terminalAuthentication`; configured terminal environment overrides apply last. System credential helpers and SSH Agent remain available. Bridges are released and pending inputs canceled on terminal exit, stop, or panel disposal; transferring a panel does not rebuild its bridge. Resources are also released if the panel closes during asynchronous creation, the count limit is exceeded, or Shell startup fails. Tokens are not written to terminal session descriptions or the Webview, and AskPass's Electron Node mode does not add extra injection to the interactive Shell.

`terminal-runtime.ts` starts a windowless `terminal-host.cjs` helper for each session. The helper lazy-loads node-pty and manages the PTY. After natural Shell exit, it delivers remaining output and the exit code, then exits and releases the native output thread. Close/terminate requests stop the Shell; the helper also has a 5-second termination fallback. The Webview retains its hidden context. Output batches use 16 ms / 32 KiB; the host keeps approximately 1 MiB of in-memory reconnection buffering, and xterm keeps 5000 lines. Output sequence numbers prevent duplicate snapshot replay and live output. At 128 KiB of unacknowledged output, reading pauses and resumes after rendering acknowledgment, preventing unbounded accumulation for slow frontends. Output and commands do not enter session persistence or logs.

The build script first clears `dist/terminal-runtime/node-pty`, copies and verifies loading of the current platform's node-pty runtime, and bundles the helper independently. Native modules do not enter the JS Bundle. Only current-platform prebuilt artifacts are retained; Linux native modules are prepared in a glibc build environment for the corresponding architecture. The packaging target must match the build machine; `--target` does not cross-compile. Before replacing the fixed package, the VSIX is extracted to a temporary directory to check identity, version, platform, workspace host, and askpass execution permissions. An independent terminal helper verifies input/output, exit, termination, and startup failure; extracted runtime files do not require project node_modules. Demo only echoes input and explicitly states that commands are not executed.

<a id="diff-and-native-editors"></a>

## Diff and Native Editors

The bottom workbench Diff is a read-only preview. Requests contain explicit comparison targets, such as Working Tree versus Index, Index versus HEAD, or Commit versus selected Parent. The host classifies results as `text`, `image`, or `binary`. Text reads complete content from both sides without truncating by line count or at 256 KiB. Each side has a 32 MiB resource-protection limit; exceeding it produces an explicit error without a partial comparison. PNG, JPEG, and WebP are identified by file signature, with at most 4 MiB read per side, a maximum dimension of 16384 pixels on either side, and at most 24 million total pixels. Base64 data is sent to the CSP-restricted Webview; an empty side indicates addition or deletion. SVG retains text semantics and is not loaded as an executable image. Other formats, oversized images, and invalid encodings return explicit reasons without exposing contents.

Only confirmed text comparisons can open in VS Code native Diff. Git text documents use the same 32 MiB per-side resource limit, returning errors rather than explanatory text that could be mistaken for file contents. Ordinary working-directory text files use real file URIs. For images and other binary files, the Webview disables native Diff and edit entries; the receiving host rereads and classifies content and rejects calls that bypass the interface. Leaf symbolic links use readlink to retrieve Git's stored link text, compare through read-only virtual documents, and do not read target contents. Parent directories still require real-path boundary checks, and ordinary text-file opening continues to validate the actual target.

Text panels obtain the complete change index through `diffPreview` with a `paged` request and read immutable snapshots by aligned line ranges through `diffPage`. The host runs Git's zero-context comparison over complete content with external Diff/Textconv disabled and retains only change-block positions. The text index stores line offsets and continuous alignment segments instead of creating an object for every context line. A page has at most 512 lines; the frontend uses 128-line pages, caches at most six pages, and renders only the viewport and nearby rows. When scroll-placeholder height exceeds 8 million pixels, logical positions are mapped so very large files remain navigable to the end, while the mouse wheel continues moving at normal line spacing. Host text and index caches total at most 128 MiB. Switching or refreshing releases old tokens; panel closure releases its snapshots, and canceled or late responses do not change the current comparison. Working-file reads check size and modification time; pagination always reads the same text snapshot from the completed comparison.

Diff loading depends on the comparison target's semantic identity. Historical comparisons do not depend on Snapshot versions. Working-directory comparisons use a separate content-refresh generation, invalidated by selected file paths, Index, relevant status, and HEAD changes for Staged comparisons. Notifications with unclear sources conservatively update the current working-directory comparison. Updating the same comparison preserves the old preview and scroll position; only changing targets clears content and returns to the top.

Cross-file navigation searches only the current ordinary Commit's complete file list and scans each candidate file at most once per round. `diffPreview` with `summaryOnly` calculates the complete change index without retaining candidate text. Once a target text file is found, its paginated snapshot is created; image results are directly reused. Text navigation follows continuous change blocks, images count as one whole-file visual change, and other binary files are skipped. The frontend retains only the current display and viewport text cache rather than loading the entire Commit's content at once. Location requests bind repository, Commit, Parent, file, and navigation mode; canceled requests or context changes discard old responses.

Deleted files in History have no working-directory entity and open using read-only Git content. Merge Commits require an explicit comparison Parent. Conflict comparisons use Index Stage 2/3 and allow opening the real file to resolve conflicts.

`resolve-and-stage` expresses Git marking and staging after the user has manually resolved content; it still uses `git add` and does not prove correctness. `operationReview` writes the current Index as an immutable Tree, scans staged changes relative to HEAD, and returns files, marker line numbers, reasons for unscanned content, and a host-issued single-use confirmation token. Tokens bind working-directory identity, branch, HEAD, Tree, and operation-control files. Continue and Commit during an active operation recheck these within the shared write queue; ordinary writes such as Stage/Abort invalidate existing tokens. Changed content after confirmation cannot reuse old confirmation. Scanning is limited to 2 MiB per file and 16 MiB cumulatively; unscanned content must be clearly shown to users. Marker detection provides reminders without guaranteeing semantic correctness. External Git processes can still race between the final check and actual Git command; Git's Index lock and execution errors remain applicable.

Native Diff and file-edit requests first route through project windows, then call `GitDocuments` on the receiving host. Virtual content registration exists only on that host. Editors use the current group and `preview: false`, preserving existing tabs and the workbench without adding a side editor group.

<a id="project-window-routing"></a>

## Project Window Routing

`ProjectWindows` registers each extension host's real workspace directories and latest activity time through `WindowBridge`. Registrations reside in the system temporary directory, isolated by VS Code data/Profile, application, and host. Each instance writes independently and renews registration periodically; registrations do not enter repositories or workbench sessions. Windows paths normalize case and resolve real directories; worktrees are distinguished by working directory.

Windows communicate through loopback IPC with random tokens, accepting only predefined requests and rechecking workspace ownership and trust. Matching priority is exact directory, longest workspace directory containing the project, then most recently active window. The receiver activates itself through native `workbench.action.focusWindow`; older versions reuse open windows by workspace identity and verify focus results. The sender waits for an execution receipt. Without an available target, `vscode.openFolder` opens a new project window and waits for extension registration; timeout reports failure. Repository and worktree project-window commands always create independent project windows. Once the new host registers, a restricted `workbench` request asks the destination to register the repository and display its workbench. The separate “Open Workbench in New Window” action uses an empty VS Code window, locates the destination through newly appearing host registration, and sends only a pathless `show-workbench` request, so this entry does not implicitly select a repository. Catalog refresh and activity broadcasts are window-level requests within the same isolation domain and do not require both windows to open the same project. They carry neither arbitrary commands nor Git parameters.

<a id="git-operations-concurrency-and-errors"></a>

## Git Operations, Concurrency, and Errors

Git uses argument arrays and `shell: false`, with additional ref and path validation and literal pathspecs for file operations. Add/Restore/Rm/Reset pass NUL-separated file scopes through standard input; Commit/Tag messages use `--file=-`. Messages containing NUL are rejected. Clean preplans all batches under a conservative argument budget and reports partial completion explicitly on failure. Oversized arguments unsupported by standard input are rejected before process startup; Stash messages are checked before preparing local state. Execution is centralized in `runner.ts`, providing output limits, timeout, AbortSignal, and noninteractive editors. Stopping waits for Git and terminator handles to close. If a write process tree cannot be confirmed stopped after a 5-second grace period, commonDir is explicitly quarantined and further writes are prohibited. Authentication resources are released only after known process handles close; root-process exit alone does not prove all descendants ended. External Git is outside the in-memory queue, so Git locks and actual command results remain the final authority.

Only one write runs at a time for the same `commonDir`. One host retains in-memory busy state; across hosts, isolated temporary-directory registrations and OS-managed loopback-port liveness leases are keyed by a hash of normalized shared Git directories. Short directory-level port mutexes serialize registration, recovery, and release. A live holder does not lose its lock because of a stale timestamp; unknown listeners, timeouts, and unavailable mutex gates cause conservative rejection. A running marker is recorded atomically before writes and remains as persistent protection if termination cannot be confirmed. Running records left by a dead host can be cleared only after native confirmation and successful lock-identity and known-process checks. The current request is not replayed; users must execute it again. Old-format registrations migrate compatibly only under their original timeout rules. The window bridge synchronizes activity start/end to other hosts and maps it to every registered worktree under that Git storage. Broadcast failures are logged, while cleanup always runs. Actual leases are checked before actions and during polling so missed end notifications can recover. Broadcasts provide interface feedback; leases enforce execution exclusion. External Git remains protected by Git's own locks. Within the write queue, GitService dynamically reads the host-provided Detached HEAD policy. Explicit Commit/Tag Checkout, Detached Stash retry, and explicit or implicit Detached worktrees are rejected by default. Stash creation and actual switching recheck policy so changes during preflight cannot bypass it. Internal Rebase operations retain their existing flow. Checkout checks the current branch, uncommitted changes, unresolved conflicts, and worktree occupancy in the host. Localizing remote branches uses full `refs/remotes/*` sources and expected OIDs. Batch creation validates all local names, upstreams, symbolic refs, and hierarchy conflicts before any write. Both batch creation and single creation-and-checkout first create refs from fixed source OIDs, then set upstream. Upstream failure accurately reports retained branches; only single creation-and-checkout continues to ordinary Checkout. Ref or upstream failure does not enter Stash or file switching. Blocked Checkout retains the branch and supports retrying the original tracking action. `Stash Changes & Checkout` reports Stash and Checkout separately. If remote-branch Checkout is blocked, retries retain the original source, name, and OID. If Stash succeeds but Checkout fails, the Stash is retained without implicit restoration or deletion. `stash.ts` supports isolated state for Stash saving/restoration; the Webview presents structured restoration blockers. The flow is described below.

<a id="selected-file-commits"></a>

### Selected File Commits

`selected-commit.ts` builds a separate Index from current HEAD and merges Index or disk versions according to the selected source. The real Index remains locked; success writes back only selected paths, preserving unselected staged content. `selected-commit-hooks.ts` uses a temporary Hooks directory for that commit and delegates to original Hooks, including custom `core.hooksPath`. At the prepared phase, `reference-transaction` compares the actual candidate commit Tree with the projection that replaces only selected paths; out-of-scope changes refuse the HEAD update. Hook formatting of selected files is allowed. Message Hooks, signing, and post-commit Hooks continue through native Commit, and command-level configuration does not override existing environment configuration. Temporary cleanup is delayed until the Git process tree is confirmed stopped. Hook side effects on disk are not guaranteed to roll back.

<a id="stash-save-and-isolated-restore"></a>

### Stash Save and Isolated Restore

`stash-drop.ts` reads the reflog while holding the Git files backend's `refs/stash.lock` and packed refs lock. It verifies the confirmed OID at the original index before rewriting the log chain and ref, preventing deletion of the wrong entry after external Git inserts one. It supports non-top entries, packed refs, shared worktrees, and SHA256. Reftable and unverifiable paths or file types refuse deletion. Publication failure attempts rollback; failed rollback retains recovery copies and locks and displays their paths. This guarantees identity checking against clients that honor Git ref locks, without promising multi-file power-loss atomicity. Read-only request scopes reject writes at the action entry, including direct file operations here.

`stash.create` without paths means global scope; nonempty paths mean the exact selected-file scope, and an empty array is rejected. Selecting either side still saves the file's complete Index and Working Tree state, including selected untracked files within that scope. The selected staged Tree uses HEAD as its baseline and replaces only selected paths. The whole Index cannot be used directly as the archive's staged parent because that would include unselected staged changes. Cleanup affects only selected paths; other file state remains unchanged. Interaction rules are maintained in the [Workbench Specification](WORKBENCH_SPEC.en.md#working-tree-and-diff).

Restoration first resolves a fixed Stash OID, checks untracked-path occupancy, and captures HEAD, original Index bytes, split Index shared files, relevant local files, effective configuration, and attribute sources. `.gitattributes` in the worktree root and relevant ancestors are captured separately without ignore filtering; missing sources are fingerprinted too, so creation, deletion, or modification of attributes invalidates old state, and attribute links are not followed. A temporary independent Git directory receives copies of the original Index and file contents and reads source objects through read-only object alternates. The copy's Index, worktree, and new objects remain within the temporary directory. Isolated commands suppress global configuration, hooks, and external program execution while retaining supported Git merge and attribute semantics. The copy runs `stash apply --index` and reads conflicts or errors. Failure returns a structured blocker containing cause, paths, Stash identity, archive retention, and the fact that this attempt did not change the real state.

After successful trial restoration, the fingerprint is recaptured and compared across HEAD, Index, local files, configuration, attributes, and split Index shared contents. Any change stops the operation. The real repository then runs `stash apply --index`. The archive is retained by default; explicit Pop calls the same safe deletion entry only after successful Apply. Deletion failure explicitly reports that changes were restored and the archive remains, preventing repeated Apply. External processes can still modify state after the final check, and actual writing can fail; preflight therefore offers no atomic rollback guarantee for real Apply. Temporary directories are cleaned on completion after verifying they belong to the intended system temporary directory.

Isolation requires Git 2.43 or newer to read system/global attribute sources. Support depends on accurate reproduction of local state: sparse checkout, affected gitlinks/submodules, active external filters, custom merge drivers, and default external merge drivers all refuse isolation. A single file over 32 MiB or total local-file snapshots over 128 MiB also refuse it. Unsupported nonordinary file types, placeholder directories that cannot be copied completely, and symbolic links in path ancestors block the operation. Completely copyable ordinary files and supported leaf symbolic links are copied according to their actual state. These limits describe AlwayGit's isolation trial capability, not Git Stash's limits. Unsupported state never falls back to trial execution in the real repository.

Fetch, Pull, and Push retain system Git Credential Helpers, SSH Agent, and configuration without overriding credential-helper interaction settings, allowing browser sign-in according to system configuration. User settings that explicitly disable interaction remain effective. When a helper does not provide complete credentials and Git requests input, each command uses its own loopback IPC AskPass bridge. Only standard HTTPS `github.com` credential requests reuse VS Code GitHub sign-in through public `vscode.authentication.getSession`. Missing sessions initiate sign-in or authorization. Usernames and tokens exist only in that command's memory, and password inquiries are answered directly when usernames are already supplied. The bridge uses the built-in GitHub Git authentication permission scope and respects disabled `github.gitAuthentication` and `git.useIntegratedAskPass`. Other hosts, SSH, disabled integrated authentication, or unavailable GitHub providers use VS Code input boxes. Cancellation or refusal of sign-in ends authentication without subsequent input boxes. Command cancellation immediately stops waiting for authentication, and late sessions are not delivered to stopped Git; the public API's sign-in UI itself cannot be canceled by AlwayGit. Ordinary queries and `ls-remote` probes continue prohibiting GCM interaction. Git terminal input stays disabled to avoid input waits in processes without terminals. Bridges use random tokens. Git timeout, cancellation, or output-limit failure immediately cancels input boxes; connection closure cancels corresponding input too. Authentication bridge resources are released after process and termination handles close; unconfirmed termination retains write quarantine. Fetch, Pull, and Push default to a 10-minute host command budget, read from `alwaygit.networkTimeoutMinutes` when each command starts. Values must be integer minutes from 0–1440; `0` disables the total duration limit, invalid configuration falls back to 10 minutes, and changes do not affect running commands. No-output notices do not terminate commands. Ordinary queries still default to 60 seconds. Webview action requests wait for the host result rather than reporting failure under the 180-second read-request timeout; waiting for native confirmation does not consume the Git command budget. AlwayGit neither persists credentials nor sends them to the Webview; system helpers may save credentials according to their own configuration. Logs and frontend errors consistently hide URL userinfo, authentication query parameters, and Authorization. Each Git command independently decodes UTF-8 streams and delivers logs only after complete-line redaction. Trailing fragments are processed on completion; lines exceeding buffer limits are safely omitted so credentials split across pipe chunks are not emitted.

Snapshot resolves the current branch's Push destination in order from `branch.<name>.pushRemote`, `remote.pushDefault`, branch remote, upstream, and a sole remote, and supplies local branch, remote branch, and upstream state as structured Webview data. The Push dialog submits explicit local and remote refspecs; remote branch names may differ from local ones. `--set-upstream` is requested only for initial tracking creation; ordinary Push with an existing upstream does not implicitly change tracking. Branch Push always explicitly selects `--follow-tags` or `--no-follow-tags`, rather than inheriting implicit Git configuration. When enabled, only annotated Tags reachable from that branch and missing remotely are included.

Tag Push uses a separate `tag.push` action and fixed-object `<confirmedOid>:refs/tags/<name>` refspec, available from single or multiple Tag selection menus. The dialog binds original Tag-object OIDs captured on opening; the host rechecks all selections before any network write. Annotated Tags do not use peeled Commit OIDs. Each Tag is pushed separately with partial-failure aggregation; explicit `--no-follow-tags` prevents configuration from including unselected Tags. Git rejects replacing a different remote Tag with the same name unless replacement is explicitly provided. Create Tag from the Tags heading inherits neither HEAD nor History selection: its target starts empty and requires explicit input. The commit-graph entry captures the right-clicked row's Commit OID and Message, locks the target read-only, and retains that identity after returning from Add Remote. Editable targets resolve to full Commit OIDs before submission to avoid moving refs during creation. Create Tag may, according to its saved default or current checkbox, push only the new Tag to the selected Remote after successful local creation. Remote failure reports partial failure and retains the local Tag for explicit Tag Push retry.

Local branch deletion first captures confirmed OIDs and atomically compare-deletes each using `update-ref --no-deref -d <ref> <expectedOid>`, preventing deletion of a replacement branch after validation. Worktree occupancy is rechecked before actual writes. Ordinary deletion judges merged state against a valid upstream or current HEAD; forced deletion still checks occupancy. Branch configuration and reflog are cleaned afterward, while recreated branches retain configuration. Batches report partial failure and stop further writes if process termination cannot be confirmed.

Tag deletion binds local and remote original ref-object OIDs captured when the dialog opens; annotated Tags do not use peeled Commit OIDs. Remote confirmation also freezes read- and Push-address fingerprints. Targets not yet queried accept the first query only if addresses remain unchanged; later refreshes cannot replace confirmed OIDs. Address or object changes disable submission and prompt reopening; submission checks current state again. Explicitly choosing another Tag or Remote recaptures identity. Local deletion uses atomic `update-ref --no-deref -d <ref> <expectedOid>` and rejects stale or missing identities; symbolic refs do not recursively delete their targets. Remote deletion is available only when the read address equals the unique Push address. It fixes remote OID and Push-address fingerprint before submission and deletes with explicit `--force-with-lease=<ref>:<oid>` to avoid removing a same-named Tag replaced after checking. Combined deletion writes remotely first and only then compare-deletes locally. Remote failure retains the local Tag; a local race after remote success reports partial failure and retains the new local object.

Remote deletion and Force-with-lease fix the remote OID and Push-address fingerprint on confirmation. Execution uses explicit `--force-with-lease=<ref>:<oid>`; an empty OID permits only a target that is still absent. Background Fetch does not update confirmed OIDs. Address changes, absent confirmation, or multiple Push addresses reject dangerous operations. After validation, the unique address is captured. Command-level `remote.<name>.pushurl` first clears the list with an empty value, then sets the captured address, preventing later pushurl changes from redirecting the operation. Temporary private system configuration first adds a literal insteadOf rule for the entire captured address, then includes the original system configuration. The entire address's longest match and earliest position prevent subsequent URL rewrites from redirecting it while preserving system settings, global/repository configuration, remote names, upstreams, and tracking refs without changing persistent configuration. Temporary files are cleaned after process completion; unconfirmed termination delays cleanup until process handles close. Before sending, the address is resolved read-only under the same overrides; execution stops if it cannot prove a unique captured address. [Git's empty-value list-clearing semantics](https://git-scm.com/docs/git-config#Documentation/git-config.txt-remotenamepushurl) require Git 2.46 or newer. Fingerprints do not expose credential-bearing addresses to the Webview. Batch deletion reports each success and failure; unconfirmed termination immediately stops subsequent operations.

Reset, Merge, and Rebase resolve targets to fixed Commit OIDs before confirmation and bind the current branch and HEAD displayed when the dialog opens. Background refreshes do not replace that identity. After host confirmation, the shared write queue rechecks state and rejects changed state, requiring refresh and reconfirmation. Reset's native confirmation shows current branch, HEAD, and fixed target. External Git can still race after the last check; Git locks and execution errors remain applicable.

The host explicitly confirms high-risk operations. If a commit encounters unsaved editor contents, it explains that Git commits the Index. Git hooks, signing, authentication, and network errors report actual failures without attempting bypasses.

<a id="security-boundaries"></a>

## Security Boundaries

Untrusted workspaces do not execute Git. The Webview uses CSP, script nonces, and restricted resource directories. Opening working-directory files validates directory boundaries and symbolic-link ancestors; only registered non-Bare worktrees can open through the workbench. Clipboard and new-window actions are handled by the host; the Webview submits only protocol-constrained data.

<a id="current-maintenance-boundaries"></a>

## Current Maintenance Boundaries

- GitService still combines queries, action validation, and execution. Workbench retains routing and use-case coordination; Store remains the unified interface-state entry. Runner, session persistence, query/snapshot coordination, and ref indexing have been extracted. Future separation should follow independent responsibilities of concrete changes, rather than file line counts alone.
- History is virtualized. Working Tree, Commit Details, Commit comparison, and Stash file lists share `VirtualFileRows`. Further performance work should continue measuring visible rows, filtering/selection cost, and interaction latency, rather than inferring overall performance only from DOM counts. Existing focused results are in the validation document.
- Stash isolation requires accurate reproduction of local state and currently retains complete capture and size limits. Reducing copied scope requires proof that attributes, Index, and unselected changes are not omitted; reducing reads alone does not justify weakening isolation protections.
- Hunk staging, interactive Rebase, and Squash/Fixup are independent requirements outside the current feature scope. This structural maintenance does not introduce those operations.
